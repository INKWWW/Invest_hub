# X 新博主当日自动激活与首次总结设计

- 关联：[V2 X 指定博主信息收集设计](2026-07-22-v2-x-information-collection-and-reader-design.md)、[X 来源身份解析与激活设计补充](2026-07-24-v2-x-source-identity-activation-design.md)、[管理员来源创建简化设计](2026-07-25-admin-source-creation-simplification-design.md)

## 1. 问题与目标

当前管理员创建 X 博主只写入一个启用但 `pending` 的来源。身份解析依赖单独的本机命令，覆盖水位又是第二个人工步骤；定时 Worker 仅发现已解析且已初始化的来源。因此“已启用”不能代表“可采集”，新博主会停在身份验证，无法在添加当日产生内容与总结。

本改进的目标是把管理员的“添加 X 博主”变为一个可恢复的当日激活请求：在本机受控 X 会话中自动核验身份，按最新已到达的上海固定窗口初始化首次连续覆盖，并完成该窗口的帖子采集、事实持久化和当日观点总结。管理员不再操作 Worker 绑定、身份验证、覆盖初始化或首次刷新。

## 2. 采集时间语义

若管理员在 T 日任意时刻添加博主，系统选择 **不晚于创建时刻的最近已到达上海固定截止点** 作为首次窗口上界。固定截止点为 `00:00 / 08:00 / 12:00 / 16:00 / 20:00`；例如 15:30 创建的来源以 T 日 12:00 作为首次完整范围上界，身份验证及初始化完成后立即处理 `(T 00:00, T 12:00]`。随后 16:00、20:00 及次日 00:00 窗口按既有连续 coverage 机制补齐 T 日后续帖子并追加相同自然日的摘要版本。

如果在一个截止点之前尚未完成激活，不伪造该截止点的完整结果。系统从尚未完成的最早范围恢复，直到赶上最近已到达的截止点。这样“当日总结”是由已验证的闭合时间范围组成，而不是把瞬时页面状态误写成完整历史。

在 T 日 `00:00` 至首次可用截止点之前添加的来源，首次范围可以是经身份核验后的空范围；空范围标为 `no_new_data`，不调用 Provider、不生成虚假摘要。当天第一个后续截止点仍会自动采集。

## 3. 自动激活状态机

创建 API 在同一数据库事务中建立来源及一个不可由浏览器篡改的 `activation` 请求。请求只携带来源 ID、创建时刻、默认参数版本及安全状态；不保存 URL、Cookie、Profile 或帖子内容。

本机 X Worker 每次 tick 先领取属于自己的待激活来源，再逐个执行以下状态机：

1. `pending`：使用专用 OpenCLI 的 `twitter profile` 验证请求账号与可见账号身份严格一致。
2. `resolved`：Worker 绑定确认后，控制面以创建时刻推导首次固定覆盖边界并原子初始化 coverage。
3. `initialized`：控制面创建或复用该来源最早的连续 `x_sync` 范围；Worker 按既有 posts + receipt 合同持久化事实、分析与自然日观点段。
4. `completed`：只有完整 receipt、事实、分析、每日视图和 checkpoint 均持久化后才记录成功。

同一来源的重复创建提交、Worker 重启或重复 tick 必须幂等：只能复用相同 activation 与连续范围，不能重置 coverage、复制 Canonical 帖子、重写既有观点段或重复触发 Provider。每个来源独立执行；一个来源的身份、网页、Provider 或持久化失败不得阻断其他来源。

## 4. 本机与权限边界

身份核验仍只发生在用户本机已登录 X 会话中，使用现有 owner-only Worker 凭据和受控 OpenCLI runtime。云端控制面不得访问浏览器 Profile、Cookie 或 X 原始页面。

新来源创建时服务端自动绑定当前唯一已注册的 X Worker；没有已注册且在线的 X Worker 时，创建请求返回可理解的“本机采集 Worker 不可用”错误，不留下永远无法完成的来源。Worker 配置改为从受控控制面领取已绑定 activation，而非手工列出单一来源；本机仍只接受相同受控 runtime 与默认 X 契约。此改进不增加第二个采集器、不使用 X API 或普通用户 Token。

普通用户不能读取或操作 activation、Worker、coverage、任务、浏览器会话或受保护诊断。管理员页面只显示安全、可理解的阶段：`正在验证`、`正在准备首次采集`、`正在总结`、`已完成`或`需要重试`，并显示经安全投影的最近完成时间；不显示来源 ID、参数版本、账户 URL、Profile、凭据、原始正文或错误堆栈。

## 5. 失败与恢复

- 身份不匹配、登录失效或网页合同失败：来源保持待重试，coverage 不创建，任何帖子和摘要均不写入。
- coverage 初始化或任务创建失败：身份结果可保留，但不得标记激活完成；下一个 Worker tick 从该阶段继续。
- 采集、Provider 或持久化失败：保留既有的失败分类和连续水位；恢复时补齐最早未确认范围。
- Worker 不可用：创建被明确拒绝，不宣称来源已启用；已有 activation 则保持可恢复状态。
- 任何失败都不得影响其他来源，也不得被读者页显示为“无新增”。

## 6. 验收标准

1. 管理员在有可用本机 X Worker 时创建一位新博主，无需额外页面或命令操作，即可进入自动激活。
2. 使用人工 fixture 覆盖：多来源交错 activation、身份不匹配、Worker 重启、创建后重复 tick、首次窗口为空、首次窗口有帖子、失败来源隔离及跨截止点同日追加总结。
3. 所有首次任务都以最近已到达的固定上海截止点作为上界；不得使用任意“现在”作为已完成边界。
4. 每个成功来源的首次窗口都通过 posts + completion receipt、原始/Canonical/分析/观点段持久化和 checkpoint 原子闭环；重复执行不产生重复事实或 Provider 调用。
5. 管理员页面准确显示激活阶段与失败可重试状态，普通用户无权访问 activation 或本机诊断。
6. 在部署后，对本次已存在的待验证博主执行受控真实验收：自动完成各自身份验证、初始化、T 日首次范围采集与 `/x` 页面验证。真实账户、帖子正文、URL、Cookie、Profile、Prompt、完整模型输出和凭据不进入 Git 或工程日志。
7. 发布前通过数据库、Worker、控制面回归、lint、production build、脱敏检查和 `git diff --check`；项目状态保持“V2 受控生产试运行”，不因此宣称无人值守 SLA 或 V2 正式可用。

## 7. 非目标与回滚

本改进不改变 Discord 方向、不扩大 X 访问权限、不支持任意历史回填、不解析媒体或外链正文，也不把新来源的 T 日范围扩展到创建前的更早日期。回滚时停止创建新的 activation 并保留未完成 activation 与既有失败事实；已完成的任务、摘要和 coverage 继续可读，绝不删除或改写既有内容。
