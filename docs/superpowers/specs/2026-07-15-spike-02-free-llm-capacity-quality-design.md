# Spike-02：免费 LLM 容量与质量验证设计

## 文档状态

- 阶段：Discovery / Spike-02 设计
- 书面状态：待用户审阅
- 本文范围：只设计 Spike-02，不授权 V0/V1 生产实现
- 设计依据：`AGENTS.md`、`README.md`、`docs/project-status.md`、`docs/intake.md`
- 已确认范围：GLM 真实评估、Mock 确定性对照；Codex CLI 不在本 Spike 中执行

## 1. 目标与第一性原理

Spike-02 只回答一个问题：

> 在不依赖复杂生产架构的前提下，GLM 是否能够以可接受的容量、稳定性和输出质量，处理 Invest Hub 后续批次总结所需的 Discord 结构化理解任务？

问题的本质不是“模型能否生成一段看起来通顺的摘要”，而是能否在输入规模增大、内容关系复杂和请求偶发失败时，仍然产出可校验、可追溯、不会错误归因的结构化结果。因此本 Spike 同时验证：

1. 输入规模扩大后，调用次数、响应时间和失败率是否可接受；
2. 输出是否能稳定解析为约定的结构化结果；
3. 关键事实、指定用户观点、标的和操作倾向是否准确归因；
4. 超时、截断、限流和 JSON 错误是否能够局部恢复；
5. 未解析的媒体或外部文章正文是否不会被模型臆测。

Spike 结果只作为 V0/V1 的设计输入，不直接批准 GLM、Prompt、chunk 参数或 Codex fallback 的生产方案。

## 2. 范围

### 2.1 包含内容

Spike 使用本地验证 harness 和两类 Provider：

- GLM：真实请求，用于测量容量、延迟、稳定性和质量；
- Mock Provider：确定性返回，用于验证统一输出契约、失败注入、局部重试和恢复逻辑。

测试覆盖：

- 小批次；
- 约 500 条消息；
- 1000 条以上消息；
- 多话题混合；
- 指定用户短句；
- 回复链和必要上下文；
- 中英文或其他多语言混合；
- JSON 输出与 Schema 校验；
- 超时、限流、截断、无效 JSON 和局部重试；
- 事实依据、指定用户归因、标的和操作倾向；
- 调用次数、重试次数和 P95 响应时间。

### 2.2 不包含内容

本 Spike 不包含：

- Codex CLI 的真实或无人值守运行；
- GLM 到 Codex 的正式 fallback 规则；
- 生产 Provider 抽象、Worker、任务队列、数据库、认证和网页；
- 正式动态分块算法或最终 token 参数；
- Discord/X 采集；
- 日累计总结和正式阅读页；
- 生产 Prompt 管理和历史摘要重算；
- 生产依赖安装；
- 将真实 fixture、密钥、完整响应或历史数据提交到 Git。

## 3. 测试输入与标注

### 3.1 Fixture 要求

测试输入由两部分组成：

1. 脱敏真实 fixture：保留消息顺序、回复关系、语言特征、Ticker、价格和观点关系；删除用户名、服务器名、频道名、头像、消息链接和其他身份信息。只保存在本地受保护目录。
2. 人工构造公开 fixture：用于仓库内可重复的确定性测试，不包含真实来源信息。

每个 fixture 必须标记：

- 消息数量和时间范围；
- 语言；
- 话题数量；
- 是否包含指定用户短句；
- 是否包含回复链；
- 是否包含未解析媒体标记；
- 是否包含标的、价格或操作倾向；
- 是否有人工标注的关键事实和禁止归因。

没有人工标注的 fixture 可以用于容量测试，但不能用于质量结论。

### 3.2 最小测试矩阵

| 规模 | 内容 | 主要目的 |
| --- | --- | --- |
| 小批次 | 覆盖多话题、短句、回复链、多语言和未解析媒体标记 | 验证结构化输出和质量基线 |
| 约 500 条 | 多话题混合，包含指定用户和普通上下文 | 验证调用规模、局部失败和批次处理能力 |
| 1000 条以上 | 多页连续输入，尽量保持真实消息密度 | 验证高消息量下的调用次数、P95、截断和最终完成能力 |

同一 fixture 可以经过脱敏或合成扩展用于不同规模，但不得通过重复同一条消息制造“质量提升”的假象。

## 4. 验证流程与边界

Spike 只定义一条可观察的验证链路：

```text
Fixture
  → 确定性预处理
  → 候选输入块
  → GLM 或 Mock 请求
  → JSON 解析与 Schema 校验
  → 必要时局部修复/重试
  → 事实与归因评估
  → 指标和证据报告
```

确定性程序负责去重、排序、作者身份标记、回复关系保留、Ticker/价格/URL 提取以及输入范围记录；这些工作不交给 LLM 判断。

Spike 可以测试少量候选输入块大小，用于观察容量和截断边界，但不在本阶段确定 V1 的动态分块算法、重叠消息数量或 Provider 安全 token 上限。

GLM 输出至少需要能够表达：

- 结构化话题或局部总结；
- 关键事实和观点类型；
- 指定用户观点及其身份标记；
- 涉及标的和操作倾向；
- 不确定性或未解析媒体标记；
- 关联的原始消息 ID。

如果输入只包含未解析媒体或外部文章链接，输出必须明确说明信息不足，不得补写文章、图片或视频内容。

## 5. 失败与重试验证

### 5.1 失败分类

每次请求和每个输入块都必须记录以下一种或多种结果：

- 成功；
- 网络超时或 Provider 限流；
- 输出截断；
- JSON 无法解析；
- Schema 校验失败；
- 内容缺失或错误归因；
- 未解析媒体臆测。

记录中不得包含密钥、Cookie、Chrome Profile 路径、私有 URL 或未经脱敏的原始正文。

### 5.2 局部恢复

- 重试只针对失败的输入块，已完成块不得重复调用；
- 实验默认最多记录三次尝试，但该数字不是 V1 的正式策略承诺；
- 超时或限流需要有界等待，不能连续快速撞击 Provider；
- 输出截断时优先缩小输入块或拆分，不直接无限重复同一请求；
- JSON 错误可以先进行程序级修复，仍失败时再进行一次短格式修复请求；
- 单个输入块最终失败时，保留已完成结果和失败证据，不能让其他块的结果丢失；
- 本 Spike 不使用 Codex CLI 自动接管失败请求。

## 6. 指标与质量评估

### 6.1 容量与稳定性指标

每次运行至少记录：

- 输入消息数量和输入块数量；
- 请求次数、重试次数和最终成功块数量；
- 首次请求成功率和最终成功率；
- JSON 可解析率和 Schema 通过率；
- 单请求响应时间 P50/P95；
- 批次总处理时间；
- 输入/输出 token 或 Provider 提供的等价用量信息；
- 超时、截断、限流和其他失败数量；
- 失败块是否可以独立恢复。

如果 Provider 不提供精确 token 数量，必须记录可重复的替代指标，并明确说明限制，不得伪造精确成本数据。

### 6.2 质量评估

质量使用固定 fixture 和人工标注检查，不比较摘要逐字一致。至少评估：

- 关键事实是否有原始消息依据；
- 核心观点是否被覆盖；
- 指定用户观点是否被正确识别和归因；
- 普通用户上下文是否被必要保留；
- Ticker、价格和操作倾向是否正确；
- 多语言内容是否发生事实丢失；
- 回复链中的观点是否被错误拆分或合并；
- 内容是否重复、空泛或引入输入中没有的结论；
- 未解析媒体是否被错误臆测。

每项质量结论都应能回指到 fixture 消息 ID 和人工标注。严重错误归因和未解析媒体臆测属于阻断级错误，不以平均分抵消。

### 6.3 初始判定门槛

以下沿用 intake 的建议门槛，作为 Spike-02 的初始参考：

- 初次 LLM 请求成功率不低于 90%；
- 有界重试后的最终成功率不低于 99%；
- JSON 可解析率不低于 98%；
- 核心观点事实有据率不低于 95%；
- 严重错误归因数量为 0；
- 未解析媒体臆测数量为 0。

P95 响应时间、批次总处理时间和调用次数必须记录并形成结论，但在本 Spec 中不预先写死一个脱离真实 Provider 配额的绝对数值。Spike 报告必须说明观测值、输入规模和是否足以支持 V0/V1 的后续设计。

## 7. 通过结论

Spike 结束时只能得出以下四类结论之一：

- **通过**：所有阻断级质量门槛满足，三档规模均有可解释的容量和恢复结果；
- **有条件通过**：质量门槛满足，但需要明确的输入块限制、低并发或其他约束才能使用；
- **不通过**：出现阻断级错误，或高消息量下无法获得可恢复、可追溯的结果；
- **未验证**：真实 GLM 条件不足，无法对关键指标作出结论，不得推断为通过。

“有条件通过”不等于批准生产实现。任何需要 Codex fallback、换 Provider 或改变产品范围的结论，都必须在后续 Spec 中单独确认。

## 8. 预期产物

Spike-02 后续若获批准进入实现，至少应形成：

- 本 Spec 对应的独立 implementation plan；
- 本地或公开 fixture 清单及脱敏说明；
- Mock Provider 确定性测试结果；
- GLM 各规模运行证据；
- 指标汇总和质量人工评估表；
- Spike-02 decision report，包含通过结论、限制、未决项和下一阶段建议。

这些产物不能把 Spike harness 直接升级为生产代码，也不能代替 V0/V1 的正式 Spec 和 Plan。

## 9. 安全与阶段门禁

- 真实密钥、真实 fixture、完整 GLM 响应和历史数据只保存在本地受保护目录；
- 公开仓库只允许人工构造的公开 fixture 和不含敏感信息的测试结果；
- 本阶段不安装生产依赖、不初始化应用框架、不创建云端资源；
- 在本 Spec 和后续 implementation plan 获得批准前，不开始 Spike-02 实现；
- 本 Spec 不固化技术栈，不批准 GLM 为正式生产 Provider，也不批准 Codex CLI fallback。
