# 普通用户邀请码时长与掩码列表设计

## 1. 问题与目标

管理员当前只能创建固定 24 小时的一次性普通用户邀请码。邀请码由一段很长的随机字符串组成，创建后仅在当前页面显示；管理员刷新页面后无法知道仍有哪些邀请码有效、各自还有多久过期。

本改进只解决普通用户邀请码的创建和可见状态：管理员可在每次创建时填写有效小时数，得到恰好 8 位、同时包含大写字母、小写字母和数字的邀请码；管理员页面可在刷新后看到该邀请码的掩码、创建时设定的有效时长、实时剩余时间和最终状态。邀请码仍只能成功兑换一次。

本改进不改变 Worker 注册邀请码。Worker 继续使用现有长随机邀请码和 1 小时创建流程，且不进入普通用户邀请码列表。

## 2. 交互与时间语义

普通用户邀请码卡片在说明文字与创建按钮之间增加一个带明确 label 的“有效时长”数字输入框，单位固定为“小时”。默认值为 `24`，可输入 `1` 到 `168` 的整数；非整数、空值或超出范围时，浏览器不得提交并给出可理解错误。

创建按钮随输入值显示“创建 N 小时邀请码”。请求只提交 `purpose: "user"` 与 `expires_in_hours: N`。浏览器不得提交 `expires_at`、创建时刻、角色或任何邀请码派生字段。

服务端在生成邀请码的同一时刻取得 `created_at`，并以同一时刻加 `N` 小时计算 `expires_at`。这两个时间写入同一记录；后续兑换只接受 `expires_at > p_now` 且尚未消费的记录。前端倒计时只用于显示，不能延长或缩短服务端有效期。

创建成功的响应仅在本次页面状态中完整展示邀请码，供管理员复制。刷新、重新访问或调用列表接口都不返回完整邀请码。

## 3. 邀请码格式、掩码和数据模型

### 3.1 普通用户邀请码

新普通用户邀请码恰好为 8 个 ASCII 字符，字符集为 `A-Z`、`a-z`、`0-9`；每一串必须至少含一个大写字母、一个小写字母和一个数字。字符类别不固定位置，避免把任何位置的熵降为常量。

服务端以密码学安全随机源生成邀请码，并在 `code_hash` 唯一冲突时有限次数重新生成。完整码不得写入数据库、日志、测试输出、证据文件、Git 或后续列表响应。

### 3.2 可刷新掩码

为满足刷新页面后仍可识别同一邀请码，普通用户邀请码记录新增 `code_mask`。其值为完整码前两位、四个 `•` 和后两位，例如 `Ab••••7Q`。列表只返回这个掩码，不返回完整码或 `code_hash`。

该掩码会持久化 4 个已知字符，因此新普通用户邀请码的验证值改为服务端私有密钥参与的不可逆校验值；数据库泄露 `code_mask` 与 `code_hash` 时，攻击者不能仅靠约 4 个未知字符离线枚举出邀请码。密钥不进入浏览器、Git、日志或数据库，部署与本地测试须通过既有 secret 管理方式提供。既有邀请码的兼容与过渡必须保持其有效期内的正常兑换，且不得把历史 hash 反推或补写为掩码。

记录新增 `validity_hours`，以保存管理员选定的整数时长，而不是由两个时间戳在读取时猜测。迁移前的历史记录因没有该值和掩码，列表显示“旧邀请码（无掩码）”与“—”；它们的现有单次消费与到期语义不变。

## 4. 管理员邀请码列表

普通用户邀请码卡片下方显示“最近创建的邀请码”，按 `created_at` 倒序展示最近 20 条 `purpose = user` 记录。每行仅含：

| 字段 | 显示 |
| --- | --- |
| 邀请码 | 新记录为如 `Ab••••7Q` 的掩码；历史记录为“旧邀请码（无掩码）” |
| 有效时长 | `validity_hours` 与“小时”；历史未知值显示“—” |
| 剩余有效期 | 有效且未使用时按 `expires_at` 每秒递减；否则显示“已过期”或“已使用” |
| 状态 | `有效`、`已过期` 或 `已使用` |

状态优先级为：已消费即“已使用”；未消费且当前时间已到或超过 `expires_at` 即“已过期”；其余为“有效”。倒计时归零时客户端立即切换为“已过期”；列表刷新或兑换时仍以服务端读到的 `consumed_at` 和 `expires_at` 为准。

列表 API 和管理员页面仅对管理员可用，返回安全 DTO，绝不包含 `code_hash`、完整邀请码、被邀请人的账号信息或服务端私有密钥。普通用户和未认证请求继续被拒绝。

## 5. 安全、失败和恢复

1. 普通用户兑换端点对失败的邀请码尝试实施来源级限制，并保持统一的无效邀请码响应，不泄露“格式错误、过期、已使用或不存在”的区别。此项与 8 位码及可见掩码共同构成暴力尝试防护。
2. 管理员创建、列表和兑换的错误响应不得回显完整邀请码、hash、掩码以外的代码字符、密钥或内部数据库错误。
3. `code_hash` 唯一冲突时只在服务端重新生成；超出有限重试次数时创建失败，不返回可能未持久化的邀请码。
4. 创建失败、浏览器刷新、列表加载失败或倒计时停止都不得改变已保存邀请码的有效期、消费状态或明文可见性。页面显示可重试的通用错误。
5. Worker 邀请码的生成、列表可见性、时长、消费流程和设备凭据流程保持原样；普通用户列表查询必须显式排除 `purpose = worker`。

## 6. 验收标准

1. 管理员可在每次创建普通用户邀请码时填写 `1–168` 的整数小时数，默认显示 24；非法输入不产生请求或邀请码。
2. 每个新普通用户邀请码恰为 8 位 ASCII 字母数字组合，且每串同时有大写、小写和数字；Worker 邀请码仍为现有长随机格式。
3. 新记录的 `created_at` 与 `expires_at` 由同一服务端生成基准计算，兑换只在未消费且未过期时成功一次。
4. 创建成功后完整邀请码只在本次页面状态中显示；刷新或列表请求只显示持久化掩码，如 `Ab••••7Q`，响应、页面和日志均不含 hash 或完整码。
5. 管理员刷新页面后可看到最近 20 个普通用户邀请码的掩码、配置时长、实时倒计时及有效/过期/已使用状态；历史无掩码记录安全降级显示。
6. 普通用户、未认证访问者和 Worker 凭据均不能读取邀请码列表；普通用户无法创建邀请码。
7. 兑换端点拒绝无效、重放、过期及超过允许频率的尝试，且不泄露具体失败原因；正常邀请兑换与既有未过期邀请码兼容。
8. 数据库迁移、控制面单元/组件/API 测试、现有 Worker 邀请回归、lint、production build、`bash scripts/v0/redact-check.sh` 与 `git diff --check` 全部通过。

## 7. 非目标与回滚

本改进不增加全局默认时长设置、不允许普通用户管理邀请码、不展示完整历史邀请码、不支持恢复完整码、不改变 Worker 注册安全模型，也不改变 Reader、来源、任务或采集能力。

回滚时停止显示新的创建控件与列表接口即可；已生成邀请码仍按其已写入的 `expires_at` 和单次消费规则处理。不得为了回滚删除邀请码记录、取消已有效的邀请码或将掩码恢复为完整明文。
