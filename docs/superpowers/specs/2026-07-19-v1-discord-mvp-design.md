## 1. 问题本质与 V1 目标

V0 已验证“本地登录态不离开用户设备”的最小采集闭环，但它只提供管理员调试界面，不能让受邀用户稳定阅读已生成的投研信息。V1 要解决的是将已验证的闭环变成一个可日常使用、可追溯且权限隔离的 Discord 阅读产品。

V1 完成后，管理员可以管理多个逻辑 Discord 来源、指定用户规则和同步任务；管理员与受邀普通用户都可以在正式网页中阅读按自然日组织的 Discord 总结、批次结果和原始消息证据。网页必须支持桌面与手机端。

这不表示 V1 已具备生产 SLA。V1 只在本 Spec 的验收范围内证明可用；跨日期长期稳定性、完整历史回填规模、自动化运维和容量扩展必须以 V1 的独立验收结果为准。

## 2. V1 范围与非目标

### 2.1 范围

V1 仅处理 Discord，并交付以下能力：

- 多个 Discord 逻辑来源，每个来源拥有独立启停状态、安全 checkpoint、任务历史和失败隔离；
- 全局指定用户规则，以及频道级的新增、停用和排除覆盖；
- 管理员配置中心：来源、指定用户规则、邀请码、Prompt 版本、Provider 状态和 Worker 状态；
- 管理员任务控制：手动触发、查看状态、局部重试、查看脱敏错误和来源级恢复入口；
- 本地 Worker 的定时触发与离线补采。默认调度时间为北京时间 08:00 与 20:50；错过时从最后安全 checkpoint 补采，而不是把错过的时间段标为空数据；
- 经 Active Adapter 采集、Canonical 映射、结构化处理后生成批次总结，并在每次成功批次后生成或更新当日累计总结；
- 正式 Discord 阅读网页：自然日 → 日累计总结 → 当天批次 → 原始消息/证据和历史版本；
- 管理员与普通用户的共享数据阅读、邀请码注册、登录和权限隔离；
- 桌面端和手机端可用的阅读体验，以及显式的处理中、部分失败、可恢复失败和成功状态；
- 原始 Discord 内容保留期、摘要长期保留和证据可追溯的数据模型与访问规则。

### 2.2 非目标

V1 明确不包含：

- X 采集、X 页面、X 配置或 Discord/X 统一体验；
- 跨频道话题聚合、跨天观点历史、长期 Topic Memory、全文搜索或投资结论推荐；
- 图片、PDF、表格、视频、语音、OCR 或外部文章正文解析；未解析内容只保留元数据、链接与明确标记；
- 用户独立信息源、独立数据空间、阅读进度、已读未读或未读数量；
- 自动 Provider fallback、GLM API、第二个真实 Provider，或将 Codex CLI 宣称为最终生产 Provider；
- 生产容量扩展、无人值守 SLA、跨地域部署迁移、桌面客户端，或第二套完整浏览器采集框架；
- 把 V0 的单页真实验证外推为无限历史回填、跨日期稳定性或持续运营已完成。

## 3. 用户、网页与权限

### 3.1 正式网页

V1 必须有正式网页，不以管理员调试页替代阅读产品。

| 页面 | 普通用户 | 管理员 | 必须呈现的内容 |
| --- | --- | --- | --- |
| Discord 阅读页 | 可访问 | 可访问 | 日期选择、频道选择、日累计总结、批次总结、原始消息证据、历史版本和状态说明 |
| 管理员来源与规则 | 不可访问 | 可访问 | 逻辑来源、启停、授权 Worker、指定用户全局规则与频道级覆盖；不显示 URL、Profile 或 Cookie |
| 管理员任务与 Worker | 不可访问 | 可访问 | 任务状态、attempt、checkpoint、脱敏失败、局部重试、Worker 心跳与版本 |
| 邀请码与运行配置 | 不可访问 | 可访问 | 邀请码状态、Prompt 版本标识与 Provider 运行元数据；不显示 Prompt 正文、凭据或完整响应 |

阅读页以内容为先：日累计总结优先于运行元数据；元数据只在状态、覆盖范围、生成时间、Provider 和失败信息确有解释价值时显示。桌面端使用左侧频道选择与主内容区；手机端使用顶部日期/频道选择和单列卡片。普通用户绝不能通过页面、API 或 RLS 读取管理配置、任务调试、Worker 信息或敏感运行数据。

### 3.2 共享数据与证据

所有用户读取同一套已生成数据。每个总结和历史版本必须回溯到对应批次、Canonical 消息和保留期内的原始消息证据；原始数据清理后，旧摘要仍可见，但证据入口必须标记为已过期，不得伪造仍可访问的原文。

## 4. 采集、处理与恢复行为

### 4.1 来源与规则

云端来源只保存非敏感逻辑 `source_id`、名称、状态、规则版本和授权 Worker。真实 Discord URL、专用 Profile、Cookie、OpenCLI 合同和私有 Prompt 继续只保留在本地受保护目录；本地维护 `source_id` 到浏览器访问目标的映射。

全局指定用户规则先作用于所有启用来源；频道级规则可新增、停用或排除指定用户。每次任务须记录实际生效的规则版本，使批次和总结可解释，但普通用户界面不暴露私有配置细节。

### 4.2 同步与历史补采

每个来源独立同步，单来源的登录、权限、页面新鲜度、Provider 或持久化失败不能阻断其他来源。管理员发起的首次历史补采必须是显式有界任务：指定来源、起止 checkpoint/页面边界和可恢复状态；不得以无限翻页作为“首次同步”。

每次同步固定遵守以下顺序：本地预检 → 领取任务 → Active Adapter 采集与逐页 telemetry → raw 事实持久化 → Canonical 验证与去重 → 指定用户/规则处理 → 分块结构化 → 批次总结 → 日累计总结版本更新 → 证据关联持久化 → 控制面确认后推进 checkpoint。任一步失败只能保留最后安全 checkpoint；重试或离线恢复从该点继续，重复消息依赖唯一身份与幂等写入消除。

V1 延续 V0 的 Active Adapter 边界：项目侧负责频道路由、分页触发、响应匹配、新鲜度、有限重试、失败分类与逐页 telemetry；不提前建设第二套浏览器采集框架。分页和单次任务的具体上限、历史补采批次大小与调度实现必须在 V1 Plan 中依据验收目标落实，不得用 V0 的单页限制或 Spike 的吞吐数字代替 V1 设计。

### 4.3 结构化、总结与媒体边界

真实结构化 Provider 候选仍是本机已登录的 Codex CLI；Mock 仅用于确定性测试。V1 起始运行参数候选为 `chunk_size=100`、最大并发 5、单请求 240 秒、最多 3 次尝试；参数不是 SLA 承诺，Plan 必须定义观测、降并发和局部重试规则。Codex 失败保留失败状态和重试入口，不自动切换 Provider。

批次总结与日累计总结必须区分原始事实、发言者观点、系统归纳和不确定判断。输出必须保存 Prompt 版本标识、Provider 运行元数据、输入 Canonical 消息范围、摘要版本与证据关系。未解析媒体或外部文章正文不得被推断；当核心信息依赖这些内容时，摘要必须明确标记信息不完整。

## 5. V1 设计选择与数据边界

本 Spec 提议在 V1 中复用 V0 已验证的控制面与本地 Worker 边界：Next.js + TypeScript 控制面、Supabase Auth/Postgres/RLS、Python 3.11+ Worker、OpenCLI Browser Bridge + Active Adapter、Codex CLI/Mock Provider。该选择只在本 Spec 和后续 Plan 获批准后作为 V1 实施选择生效；它不是永久生产技术栈承诺。

V1 必须扩展但不破坏 V0 的 `sources`、`sync_tasks`、`checkpoints`、raw/Canonical 消息、结构化运行、证据关联、任务事件和角色边界。新增的阅读与总结数据至少要表达：来源、自然日、批次、输入消息范围、摘要版本、日累计版本、覆盖状态、证据关联和原始保留期。Plan 必须给出确切表、索引、RLS policy、接口和向后兼容迁移顺序。

任何 checkpoint 只在 raw、Canonical、结构化结果、批次/日累计版本和必要证据关系均成功持久化、且控制面确认后推进。所有任务事件只追加；不能通过覆盖旧状态抹去失败、重试或摘要版本事实。

## 6. 安全与运行约束

- 专用浏览器 Profile 只登录 Discord，不登录邮箱、金融账户或其他无关账号；不自动化普通用户 Token，也不调用 Discord 直接 REST API。
- Cookie、Token、密码、真实 URL、Profile 路径、私有 Prompt、完整模型响应、真实 fixture、历史正文和本地 evidence 不得进入 Git、Vercel、云端调试页、普通日志或任务 payload。
- 管理员操作与普通用户阅读必须在路由、API 与 RLS 三层隔离；共享阅读数据不等于共享配置或运行诊断。
- 原始 Discord 内容按保留策略保存一年，摘要和摘要版本长期保存；实际清理任务、日志清理和全系统生产运维仍属 V3，V1 不得在没有批准 Plan 的情况下实施删除作业。
- 真实页面验证只使用用户已加入且网页中正常可见的频道；登录失效、无权限、missing/stale response、错误 cursor、Provider timeout 和 Schema 错误必须分类失败，不能伪装成“无新数据”。

## 7. V1 验收标准与退出门槛

### 7.1 产品与权限验收

1. 管理员和普通用户可在正式登录网页中读取相同的已生成 Discord 内容；普通用户可完成日期、频道、批次、原始证据和历史版本的阅读流程。
2. 阅读页在桌面与手机宽度均可完成上述流程，不以管理员调试页或桌面专用布局替代。
3. 普通用户无法通过路由、API 或 RLS 访问来源配置、指定用户规则、邀请码、任务调试、Worker 心跳、Prompt 正文、Provider 凭据或完整模型响应。
4. 管理员可管理至少两个逻辑 Discord 来源，并为指定用户配置全局规则及一个频道级覆盖；规则变更只影响后续任务，并可从批次元数据识别实际规则版本。

### 7.2 数据、同步与恢复验收

5. 两个来源分别完成真实授权 Discord 增量同步，各自创建、持久化和推进独立 checkpoint；第二次同步不产生重复 Canonical 消息。
6. 管理员可对一个来源启动显式有界的历史补采；中断或 Worker 离线后恢复任务从最后安全 checkpoint 继续，未确认数据不被跳过，其他来源任务仍可运行。
7. 某一来源的登录、权限、页面、Provider 或持久化失败会形成脱敏且可操作的失败分类；不前移该来源 checkpoint，也不把失败伪装为 `no_new_data`。
8. 每个成功批次产生可追溯的批次总结；当日累计总结在该批次持久化成功后创建新版本或更新当前版本，并可回溯其输入范围和证据。
9. 测试 fixture 和至少一次真实授权运行都证明：事实、发言者观点、系统归纳、不确定判断和未解析媒体标记未被混淆；严重错误归因和媒体臆测均为 0。

### 7.3 工程、安全与发布门槛

10. 单元、集成、RLS、Worker 和端到端测试覆盖多来源 checkpoint、规则覆盖、摘要版本、失败隔离、离线恢复、权限阻断和阅读数据查询；真实数据不进入测试 fixture 或仓库。
11. 本地受保护 evidence、部署日志、管理员调试页和 Git 均不包含凭据、Profile、真实 URL、私有 Prompt、完整响应或真实正文；最终提交前运行项目脱敏检查与 `git diff --check`。
12. V1 Final Report 逐项记录通过、条件通过或失败，并说明真实验证覆盖范围、已知稳定性限制和未决项。只有第 1–11 项均通过，V1 才能称为“Discord 正式可用 MVP”；任何权限绕过、checkpoint 越界、事实丢失、重复写入、不可追溯总结或敏感信息泄露均为阻断失败。

## 8. 交付物、顺序与阶段门禁

本 Spec 获批准后，下一步是编写 V1 implementation plan。Plan 必须先定义：数据迁移和兼容顺序、阅读路由与查询边界、管理员配置接口、Worker 的多来源调度与恢复语义、历史补采的有界参数、测试矩阵、真实页面验收与回滚方案。

V1 实施完成时必须产出：V1 Plan、工程日志、脱敏 Final Report、公开 fixture 测试结果、仓库外受保护的真实页面 evidence、更新后的 `project-status.md` 与文档导航。V1 通过后才能讨论 V2 X 或 V3 生产运维范围。

在本 Spec 与 V1 Plan 分别获得用户批准前：

- 不创建或修改 V1 应用功能、数据库迁移、Worker 行为、生产依赖或部署配置；
- 不把 V0 的临时参数、隔离 Preview 或真实单页结果称为 V1 生产默认值；
- 不开始 X、自动 fallback、多来源生产运营或正式上线。

## 9. Spec 自检

- 产品检查：明确承诺 V1 包含桌面/手机正式阅读网页，而非管理员调试页。
- 范围检查：只包含 Discord MVP；X、跨频道聚合、媒体解析和模块 2–4 已排除。
- 事实检查：V0 的有界单页闭环是设计输入，不被外推为长期运营能力。
- 数据检查：多来源、规则版本、批次/日累计版本、证据、保留期与 checkpoint 的关联均有明确边界。
- 安全检查：本地浏览器登录态与真实内容不离开受保护边界，管理员与普通用户权限分层明确。
- 阶段检查：本文为 Draft，不授权实现；V1 Plan 必须独立审阅和批准。
