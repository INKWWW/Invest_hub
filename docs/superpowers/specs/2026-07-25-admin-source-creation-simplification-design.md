# 管理员来源创建简化设计

## 文档状态

- 阶段：V2 后的管理员可用性改进
- 状态：**用户授权自主批准；已合并并部署**
- 日期：2026-07-25
- 设计对象：`/admin/sources` 中的 Discord 与 X 新建表单
- 关联：[管理员信息来源配置工作台设计](2026-07-25-admin-source-configuration-workspace-design.md)

## 1. 问题与目标

管理员创建来源时，当前页面要求填写“内部来源标识”和“参数版本”。前者是任务、覆盖边界和历史事实关联所需的机器唯一键；后者是 Worker 与任务之间的采集契约版本。两者都不是管理员创建一个频道或博主时需要作出的业务判断，手动输入既容易出错，也不能帮助完成创建。

本设计的单一目标是：管理员只描述要跟踪的来源，系统自动创建且托管技术身份与默认采集契约。

## 2. 交互决定

### 2.1 只收集管理员可理解的信息

Discord 创建表单只收集“显示名称（社区名 · 频道名）”。X 创建表单只收集“X 账号”和“展示名称”；X 账号置于前面，输入后可将带 `@` 的账号自动建议为展示名称，管理员仍可覆盖展示名称。

两类表单均明确显示非编辑状态“采集方案：标准采集（推荐）· 系统自动维护”。这是一条说明，不是隐藏输入，也不是包含虚假版本的下拉菜单。

### 2.2 系统托管技术值

服务端在创建请求通过校验后生成不可猜测的 `source_key`，格式为 `<source_type>:<UUID>`；浏览器请求、表单 DOM、成功响应及状态文案都不携带该值。

服务端依据来源类型选择唯一的当前稳定默认版本：Discord 使用 `discord-standard-v1`，X 使用 `x-standard-v2`。该值仅写入来源与后续任务快照，以保证 Worker 不会把不兼容的任务和来源混用；创建用户不能覆盖它。

当前没有第二个经验证、可供管理员选择的采集契约。因此页面不提供“旧版”“高级”或任意输入选项。将来只有当存在真实、受支持且说明了影响的替代契约时，才可把这条只读说明升级为带人类可读标签的选择控件。

### 2.3 清晰的创建反馈

成功时，Discord 提示“Discord 来源已创建。下一步：配置采集范围。”；X 提示“X 博主已创建。下一步：完成身份验证并初始化覆盖范围。”。失败提示指出应检查的业务输入或管理员权限，不提示内部键、版本、URL、Profile、Cookie、Worker 凭据或原始内容。

## 3. 数据、接口与安全边界

1. 不迁移数据库、不修改已有来源的 `source_key` 或 `parameter_version`，也不改变任务、coverage、checkpoint、Worker 或 Reader 的既有语义。
2. Discord `POST /api/admin/sources` 仅接受 `{ display_name }`；X `POST /api/admin/x/sources` 仅接受 `{ display_name, requested_handle }`。任一额外键（包括 `source_key`、`parameter_version`）均以 `422` 拒绝。
3. 两个路由继续使用现有管理员角色校验；系统生成的值仅在服务端传入既有 repository/RPC。
4. 创建成功响应只返回创建状态、类型、展示名称和 X 的安全身份状态；不得返回 UUID、内部键、参数版本、URL、Cookie、Profile、Worker 或 Provider 信息。
5. 浏览器不生成技术身份，避免可预测、重复或被篡改的来源键；重复来源的现有数据库约束和安全错误处理保持有效。

## 4. 视觉与可访问性

表单沿用信息来源工作台的纸面层级：字段是管理员的“来源资料”，标准采集方案使用低对比说明带，既解释系统会处理什么，也不与可编辑字段竞争。X 账号输入采用等宽 `@` 前缀提示，展示名称维持正常正文样式。

所有输入有显式 label、可见焦点和移动端不小于 44px 的操作目标。自动建议展示名称不得覆盖已经由管理员修改过的内容；键盘与读屏用户可不依赖自动建议完成表单。

## 5. 验收标准

1. Discord 页面只显示显示名称和“标准采集（推荐）· 系统自动维护”说明；X 页面只显示 X 账号、展示名称和同一说明；两者均不显示或提交“内部来源标识”“参数版本”。
2. X 输入账号后仅在展示名称尚未被管理员编辑时建议 `@账号`；管理员编辑后再次修改账号不得覆盖名称。
3. 两个 POST 路由拒绝旧技术字段和未知字段，服务端生成来源键与默认版本，并只返回安全创建 DTO。
4. 普通用户仍无法创建来源；成功和失败文案不泄露技术身份、URL、Profile、Cookie、Provider 或原始内容。
5. 组件与 API 测试覆盖上述边界，并通过全量前端测试、lint、production build、脱敏检查与 `git diff --check`。
