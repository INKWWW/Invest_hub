## 1. 问题本质与 V1.1 目标

投资研究阅读的价值取决于“这段时间内的全部可见讨论是否被覆盖”，而不取决于请求了多少 Discord 网络页。网络分页只是读取接口的传输细节，不能成为业务完成条件。

当前 V1 把 `max_pages` 写入普通增量任务、Worker 和定时任务：控制面默认 5 页，Adapter 在达到该页数后停止。它还以 `before=<checkpoint>` 继续分页。这意味着首次无 checkpoint 时可能从最新消息开始读取有限页数，而之后的任务会继续读取 checkpoint 之前的更旧历史，无法满足“从上一个已完成时间点到本次时间点”的连续更新语义。当前定时循环只有命令入口，尚无运行中的本地常驻调度服务。

V1.1 的目标是把 Discord 变成可验证的持续信息流：每个已启用来源按上海时区的固定时间窗完整采集；管理员可在定时窗外将一个指定频道更新到当前时刻；页面把已配置作者当天的核心判断和频道讨论的不同观点清楚呈现给所有阅读用户。任何无法确认完整性的区间都必须保持未完成，不能以“已抓若干页”或“无新数据”结束。

## 2. 已确认的产品决策

### 2.1 固定定时窗

所有定时窗使用 `Asia/Shanghai`，其名义结束时间、正常无中断时的覆盖区间如下：

| 触发时刻 | 正常覆盖区间 |
| --- | --- |
| T 日 00:00 | T-1 日 20:50 ～ T 日 00:00 |
| T 日 08:00 | T 日 00:00 ～ T 日 08:00 |
| T 日 16:00 | T 日 08:00 ～ T 日 16:00 |
| T 日 20:50 | T 日 16:00 ～ T 日 20:50 |

区间采用 `(start_at, end_at]`：上一已确认截止点本身不重复计入，当前截止点的消息计入本窗。消息 ID 去重仍是额外保护，不能替代时间窗完整性。

### 2.2 不再有页数型成功条件

定时和管理员手动更新均**不得**使用 `max_pages`、页数、消息条数或运行时长作为“本窗已完成”的条件。Worker 可以逐页请求、续租、重试或跨多个尝试恢复，但只有确认已越过本窗 `start_at` 的下界后才能标记 `range_complete=true`。

每页仍必须保留 Active Adapter 已验证的频道路由、响应匹配、新鲜度检查、有限单页重试、错误分类和 telemetry。它们是传输可靠性保护，不是对可采集历史长度的限制。

### 2.3 管理员作者配置与阅读输出

管理员按“已绑定 Discord 频道 + 指定 Discord 用户”配置作者卡片。每位启用的指定作者，在该频道当天已完成覆盖范围内有消息时，必须生成一张作者卡，包含：

1. 作者名；
2. 截止当前覆盖时间的核心逻辑，分别说明大盘趋势和个股判断；
3. 大盘和个股操作倾向，如原文未表达则明确“未表达”；
4. 投资方法论层面的策略建议，不得伪装成具体个股买卖建议；
5. 不确定性、未解析媒体或证据不足的明确说明。

同一频道的整体输出必须按讨论话题组织。每个话题至少给出讨论概述，以及零个或多个“观点”条目；每条观点必须保留提出人的显示名、其观点/推理、如有的操作倾向以及可验证的消息证据 ID。系统归纳必须和原作者观点清楚区分。

### 2.4 管理员手动更新

`/discord` 阅读页在管理员选择频道后显示“更新至当前时间”按钮。它只创建该频道的排队任务，不直接控制本地 Chrome。普通用户既看不到按钮，也不能调用对应 API。

手动任务的 `end_at` 由控制面创建任务时的可信服务器时钟固定；其 `start_at` 是同一来源最后一个已确认完成的覆盖截止点。正常情况下，这让管理员可以在两个定时窗之间获得最新观点；发生失败时，它也确保未完成时段不会被跳过。

## 3. 范围与非目标

### 3.1 范围

V1.1 仅在 V1 已有 Discord 读取、权限和证据边界上增加或替换以下能力：

- 四个上海时区定时窗的本地常驻调度与恢复；
- 面向完整时间区间的采集、任务状态、覆盖水位和失败恢复模型；
- 管理员频道级指定作者配置；
- 指定作者日内卡片和频道话题/观点输出；
- 管理员在正式 `/discord` 页按来源发起手动更新、查看排队或处理状态；
- 对应的数据库迁移、Worker/控制面契约、Prompt/结构化 Schema、阅读查询、权限、确定性测试和真实授权验收。

### 3.2 非目标

V1.1 不包含：

- X、其他来源、跨频道话题聚合、跨天观点记忆、全文搜索或交易执行；
- 图片、PDF、表格、视频、语音、OCR 或外部文章正文解析；
- 直接 Discord REST API、普通用户 Token、第二套浏览器采集框架、自动 Provider fallback 或新 LLM Provider；
- 普通用户创建来源、作者配置、手动更新、查看 Worker/任务/检查点诊断；
- 以作者卡片输出个股交易指令、收益承诺或未经原文支持的确定性判断；
- 将本地 macOS Worker 扩展为云端浏览器集群或承诺无人值守 SLA。

## 4. 完整时间窗采集契约

### 4.1 两类时间点

每个来源维护两个不同的状态，不能再混为一个不透明的 cursor：

| 状态 | 含义 | 用途 |
| --- | --- | --- |
| `coverage_through_at` | 最近一个已完整持久化、已生成摘要并获控制面确认的时间上界 | 决定下一个任务的 `start_at` |
| `resume_cursor` | 当前尚未完成任务已安全读取到的 Discord 历史页游标 | 仅用于该任务的断点恢复 |

已有 V1 的 `safe_checkpoint` 保留为历史审计字段，但 V1.1 不得把它当作“已经连续覆盖至某一时间”的证据，也不得继续以它驱动新消息的常规同步。

### 4.2 任务范围与顺序

每个 V1.1 任务都有不可变的 `capture_range`：

```json
{
  "mode": "window",
  "trigger": "scheduled | manual | bootstrap",
  "timezone": "Asia/Shanghai",
  "start_at": "ISO-8601 instant",
  "end_at": "ISO-8601 instant",
  "scheduled_window_key": "YYYY-MM-DDTHH:mm+08:00 | null"
}
```

`start_at` 在领取任务时从该来源当前 `coverage_through_at` 固化；`end_at` 对定时任务是其名义触发时刻，对手动任务是按钮请求被控制面接受的时刻。来源内任务必须按 `end_at` 串行领取：一个较早的区间没有成功前，不得让较晚区间越过它成功。

因此，在没有手动更新或失败时，任务范围与第 2.1 节的固定表完全一致。若管理员在 10:30 成功手动更新，下一次 16:00 的任务范围是 `10:30 ～ 16:00`；若 08:00 任务失败，16:00 前必须先恢复从最后完成水位开始的缺口，不能把 08:00～16:00 伪装成独立完整窗。

### 4.3 采集与完成判定

1. Worker 领取任务后先记录 `end_at` 快照，再从频道最新可见消息向历史方向分页；运行较晚时，`end_at` 之后的新消息不能混入本窗。
2. 每页均持久化其 raw/Canonical 事实和 `resume_cursor`，并严格验证 Browser Bridge 返回的是新鲜、匹配的 Discord 页面。
3. Worker 继续分页，直至一个已验证页面证明其最旧可见消息已早于或等于 `start_at`，或一个已验证的空页证明频道在该方向没有更多消息。
4. 仅将 `(start_at, end_at]` 内的 Canonical 消息纳入本窗；范围外消息可用于边界判断，但不得进入本窗摘要。
5. 在所有范围内消息、结构化输出、批次/日累计摘要和证据关联持久化并得到控制面回执后，才将 `coverage_through_at` 原子前移至 `end_at`，并记录 `range_complete=true`。
6. 任一页的新鲜度失败、权限/登录失败、cursor 异常、持久化失败、Provider 超时或 Schema 错误，均令任务保持可恢复失败；不得前移 `coverage_through_at`，不得显示为成功或无新数据。

当本窗内没有消息时，只有在第 3 步的边界被验证后才能生成 `no_new_data` 成功结果，并把水位推进至 `end_at`。这表示“已证明没有消息”，不是“未继续翻页”。

### 4.4 离线、重试与启动初始化

本地 Worker 必须以 owner-only 配置和专用 Discord Chrome Profile 作为 macOS `launchd` 常驻 Agent 运行。它在登录后自动启动、每分钟检查一次四个时间窗，并在机器睡眠后唤醒或进程重启时补投递所有错过的名义时间窗；Vercel 不承担浏览器采集或本地登录态任务。

同一来源的错过窗口必须按时间顺序补齐，没有“最多补几个窗口”的截断。单页网络重试可以有限，逻辑任务的页数不可有限；长区间可通过已持久化的 `resume_cursor` 在多次 lease/进程恢复中继续。

V1.1 首次启用某个来源前，管理员必须在来源配置中选择一个上海时区的既定窗口边界作为 `coverage_start_at`。系统从该明确边界补采到最新已到期窗口；旧 V1 cursor 或旧摘要不得自动被推断为已完整覆盖。这样首次覆盖范围有可审计的下界，不会把未知历史误标为完整。

## 5. 作者配置、结构化理解与摘要

### 5.1 作者配置

作者配置以频道为作用域，不再将“全局 target/exclude 规则”作为作者卡片的唯一产品入口。新增的作者卡片配置必须包含：

```json
{
  "source_id": "UUID",
  "author_id": "stable Discord account ID",
  "author_display": "last observed display name",
  "author_handle": "last observed username or null",
  "enabled": true
}
```

管理员在来源下拉框选择频道，然后从该频道已采集消息的作者列表中搜索并选择用户。页面显示 `display name (@handle)`，实际保存稳定 Discord account ID；同一频道/作者只能有一条启用配置。没有已观察到消息的用户不能凭显示名自由写入，以免同名、改名或错误归因。管理员可停用或删除配置，变更只影响后续领取的任务快照，既有摘要版本保持可追溯。

### 5.2 两层结构化处理

Codex CLI 继续是唯一真实 Provider 候选，Mock 仅用于确定性测试。每项结构化结论必须有本窗 Canonical 消息 ID 支撑；未解析媒体只能标记，不能补全其内容。

第一层按可恢复的消息 chunk 提取可验证的事实单元：发言人、主题候选、原作者观点、推理、操作倾向、方法论、未解析媒体和不确定性。第二层只以这些已验证单元及其消息关系汇总成日内作者卡和频道话题，不重新把未验证原文当作事实。两层输出均须有严格 JSON Schema，未知字段、未知消息 ID、配置外作者卡、缺失作者 ID 或不完整媒体关联必须失败。

### 5.3 日累计输出 Schema

`daily_summaries.output` 的 V1.1 当前版本必须只包含以下 allowlist 字段；阅读层对未知字段 fail closed：

```json
{
  "schema_version": "v1.1",
  "natural_date": "YYYY-MM-DD",
  "as_of": "ISO-8601 instant",
  "author_cards": [
    {
      "author_id": "Discord ID",
      "author_display": "string",
      "core_logic": {
        "market_trend": "string | null",
        "stock_judgments": [
          {
            "subject": "ticker, company, or null",
            "judgment": "string",
            "reasoning": "string | null",
            "source_message_ids": ["string"]
          }
        ]
      },
      "operation_tendency": {
        "market": "string | null",
        "stocks": "string | null"
      },
      "methodology": ["string"],
      "uncertainty": ["string"],
      "source_message_ids": ["string"]
    }
  ],
  "topic_discussions": [
    {
      "title": "string",
      "summary": "string",
      "viewpoints": [
        {
          "author_id": "Discord ID",
          "author_display": "string",
          "viewpoint": "string",
          "reasoning": "string | null",
          "operation_tendency": "string | null",
          "source_message_ids": ["string"]
        }
      ],
      "uncertainty": ["string"],
      "source_message_ids": ["string"]
    }
  ],
  "warnings": ["string"]
}
```

空数组和 `null` 必须表达“没有足够原文支持”或“作者未表达”，不得由模型补写。`natural_date` 按 `Asia/Shanghai` 归属；`as_of` 取最近一个成功完成的 `end_at`。每次完成一个影响该自然日的窗口后，系统从该日所有已完成范围内的结构化单元生成新的 append-only 日累计版本。

## 6. 网页、权限与可追溯性

### 6.1 阅读页

正式 `/discord` 页面继续以内容为先，并在 V1.1 调整为以下顺序：

1. 频道和日期选择；
2. 该日“截至 `as_of`”的指定作者观点卡；
3. 该频道按话题整理的讨论与署名观点；
4. 需要时展开的批次/版本历史和简明覆盖状态。

作者卡和观点条目必须显示作者名，但默认阅读界面不得恢复 V1 已移除的原始聊天列表、“Evidence-backed messages”模块、local raw 路径、Worker 诊断、Prompt/Provider 信息或实现性说明。消息 ID、证据关系、任务和 raw 数据仍在后端保留一年以满足可追溯性；普通阅读 DTO 不返回 raw 正文或本地引用。

桌面与 375px 窄屏均必须支持完整阅读。未有作者卡、没有话题、正在处理、可恢复失败和覆盖不完整必须以不同状态呈现，不能显示为“今日无讨论”。

### 6.2 管理员操作与访问控制

管理员在所选频道旁可见“更新至当前时间”按钮及该来源最近任务的安全状态。点击后：

1. 控制面以当前来源和可信 `end_at` 创建或复用一个活动中的手动任务；
2. 同一来源存在未完成任务时返回该任务，而不是创建并发重复抓取；
3. 页面轮询或刷新任务状态，成功后读取新的日累计版本；
4. Worker 离线时任务仍可排队，页面说明“等待本地 Worker”，但不泄露 Profile、URL、Cookie 或凭据。

`POST` 手动更新 API、作者配置 API、任务状态中的管理诊断、`coverage_through_at` 和 `resume_cursor` 均仅限管理员。在路由守卫、API 授权和 Supabase RLS 三层验证；普通用户的直接请求必须得到 403，不能只依赖前端隐藏按钮。

## 7. 数据迁移与兼容边界

V1.1 Plan 必须提供一份可回滚 migration，至少完成以下数据模型调整：

| 对象 | V1.1 要求 |
| --- | --- |
| `sync_tasks.collection_scope` | 用 `capture_range` 取代 `incremental/history + max_pages`；拒绝所有含 `max_pages` 的 V1.1 常规或手动任务。 |
| `source_coverage_state` | 每来源一行，保存 `coverage_through_at`、最近成功任务、初始化边界和更新时间；只有完整范围回执能推进。 |
| `sync_task_capture_progress` | 每任务保存不可变范围、`resume_cursor`、分页 telemetry、范围完成状态和错误；用于断点恢复，不可当作来源完成水位。 |
| `scheduled_sync_windows` | 窗口 key 接受 `00:00`、`08:00`、`16:00`、`20:50`；以 `(source_id, window_key)` 幂等，不再写入页数。 |
| `source_author_profiles` | 保存频道级稳定作者 ID 与最后观察到的安全显示字段；管理员可管理，普通用户不可读取配置细节。 |
| `summary_batches` / `daily_summaries` | 允许并验证 V1.1 输出 Schema、完整覆盖元数据、作者卡及署名观点；历史 V1 摘要仍可读取。 |

现有 V1 `source_author_rules`、raw/Canonical 消息、证据、摘要版本、RLS 和普通阅读权限应保留。V1.1 迁移不得删除真实内容、缩短保留期、暴露本地 raw 引用，或把已完成 V1 历史任务重写为“已按时间窗完整覆盖”。

## 8. 验收标准

### 8.1 时间窗与恢复

1. 在上海时区，调度器分别在 00:00、08:00、16:00、20:50 创建可幂等的来源任务；重复 tick 不生成第二个同来源同窗口任务。
2. 无手动任务或失败时，四个任务的固化范围精确等于第 2.1 节四个区间。
3. 每个成功任务在 Discord 消息足以超过 5、25 和 100 个网络页的公开 fixture 中，仍持续读取至其 `start_at` 边界；任务 payload、数据库约束、API、前端和 Worker 不存在 `max_pages` 成功上限。
4. Worker 在页面 6、任意后续页或 Provider 阶段失败时，`coverage_through_at` 保持不变；恢复后完整补齐同一缺口，消息不重复，后续窗口不越过该缺口成功。
5. 机器离线跨过至少三个窗口后恢复，系统按时间顺序创建并完成所有错过窗口；不把未运行窗口标为无数据。
6. 定时任务因调度延迟在 `end_at` 后开始时，只摘要 `(start_at, end_at]` 内消息；延迟期间的新消息保留给随后窗口或手动任务。
7. 首次启用来源必须显式设置合法 `coverage_start_at`；无法初始化时不得启动时间窗同步，也不得从旧 V1 cursor 推断覆盖完整性。

### 8.2 作者、摘要与阅读

8. 管理员可为至少两个不同来源各配置一位已观察作者；同名显示名不能导致错误绑定，持久化键为 Discord account ID。
9. 每位配置作者在当天有足够原文时，日累计输出和页面均包含第 2.3 节五项内容；无原文支撑的字段为 `null`、空数组或明确不确定性，而非模型猜测。
10. 每个频道话题至少能呈现两位作者的不同观点及各自显示名；每一观点的所有证据 ID 都属于本来源、当前自然日和已完成范围。
11. 未解析媒体、外部正文缺失、互相矛盾观点和证据不足均在作者卡或话题不确定性中可见；不得形成确定性投资结论。
12. 阅读页桌面和 375px 宽度均显示作者卡和话题观点；默认 HTML/API 不包含原始消息正文、`local_raw_ref`、“Evidence-backed messages”、Worker、Prompt 或凭据。

### 8.3 手动更新、安全与运行

13. 管理员在 `/discord` 为选定频道点击一次“更新至当前时间”，只创建或复用一个该来源活动任务；成功后页面可读到新的 `as_of` 版本。
14. 普通用户不能看到按钮，调用作者配置、手动更新、任务和覆盖状态 API 返回 403，RLS 也拒绝直接读取。
15. 已安装的本地常驻 Agent 在重启后自动恢复；管理员页能读取脱敏的最后心跳、下一名义窗口和最近调度结果，不包含本地路径或凭据。
16. 公开 fixture 单元/集成/E2E 测试覆盖第 1–15 项；真实授权双来源验证覆盖四窗中的至少一次完整定时窗、一次页面超过 5 页的完整窗口、一次手动更新、一次中断恢复和普通用户阅读。
17. 实施前后均运行项目脱敏检查和 `git diff --check`；真实 Discord 正文、URL、Profile、Cookie、私有 Prompt、完整模型响应和本地 evidence 不进入 Git、Vercel 或公开 fixture。

## 9. 实施顺序、回滚与明确不触碰项

实施必须在独立 V1.1 Plan 获批后，按以下依赖关系推进：

```text
时间窗数据模型与 RLS
  ├── 来源覆盖水位、任务范围和恢复状态
  │     └── Worker 分页、常驻调度与控制面 API
  └── 频道作者配置与结构化 Schema
        └── 日累计摘要、阅读 DTO 和 /discord 页面
所有上述能力 ──> 定义测试、真实授权验收、部署与文档更新
```

先建立可证明的范围完成条件，才能安全地生成观点和把结果展示给用户；先完成稳定作者 ID 配置和 Schema，才能避免作者卡发生同名或无证据归因。

回滚时，新创建但未完成的 V1.1 任务必须停止并保持原水位；已写入的 V1.1 摘要版本以 append-only 方式保留，并将 reader current 指针切回上一个有效版本。只在迁移明确验证后才允许删除新的空配置或表结构，绝不删除 V1 raw/Canonical/证据历史。回滚不能把 V1 已有的有限分页 cursor 重新解释为连续时间覆盖。

以下已有能力不得因 V1.1 被回退：V1 的管理员/普通用户权限隔离、逻辑来源绑定、原始事实与证据保留、Active Adapter freshness 校验、分类失败、媒体不臆测、脱敏边界，以及默认阅读页不展示 raw/evidence 调试模块的产品决定。

## 10. 后续阶段门禁

本文已获用户批准；下一步只能是编写并批准独立的 V1.1 implementation plan。Plan 必须列出确切 migration、RPC/API 形状、LaunchAgent 安装与卸载步骤、Prompt/Schema、测试矩阵、真实授权验收、部署目标和回滚命令。

在 V1.1 Spec 与 Plan 分别批准前：

- 不修改 `max_pages` 相关代码或迁移；
- 不创建 launchd Agent、定时任务、手动更新按钮、作者配置表或新 Prompt；
- 不执行真实 Discord 采集、部署或数据库迁移；
- 不把 V1.1 需求表述为 V1 已通过的持续运营能力。

## 11. Spec 自检

- 时间完整性：定时窗、手动窗、失败恢复、离线补窗、延迟执行和首次初始化均有明确上下界。
- 产品内容：指定作者五项卡片字段、频道话题和署名观点均已定义，且要求原文证据与不确定性。
- 页数边界：`max_pages` 不再出现在 V1.1 正常成功路径；分页只服务于抵达时间边界。
- 安全边界：本地浏览器登录态、真实内容和管理操作仍与普通阅读隔离。
- 阶段边界：本文已批准，但仍不授权实现；V1.1 Plan 必须独立批准。
