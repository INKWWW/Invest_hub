# Discord 嵌套消息容器滚动能力 Spike 设计

## 文档状态

- 阶段：独立技术 Spike / 不属于 V1.1 生产恢复
- 状态：**Draft；等待用户审阅批准后执行**
- 日期：2026-07-23
- 前置事实：现有 OpenCLI `browser scroll` 只滚动页面 viewport；先前的普通页面滚动和聚焦后的按键均未推动 Discord 嵌套虚拟消息列表，也未触发新的历史消息响应。

## 1. 唯一问题

> 在用户本人已加入且明确允许测试的一个既有 Discord 频道中，能否通过受控的、指定消息列表容器的只读滚动，连续触发至少两次新的历史消息响应？

本 Spike 只验证历史翻页的交互能力；不验证 500 条高水位增量、不运行 Worker、不持久化消息、不生成摘要、不部署，也不恢复 Discord 的生产采集。

## 2. 安全与数据边界

- 用户手动在专用 Discord Chrome Profile 中打开目标频道，Agent 仅绑定该既有标签；真实 URL 不写入聊天、文档、Git 或 fixture。
- 仅使用用户本人可见且明确允许用于本次测试的频道；不发送、编辑、删除消息，不访问其他频道。
- 不截图、不启用 `retain-on-failure` trace，不把原文、作者、频道名、消息 ID、Cookie、Token、Authorization、请求头或 Profile 路径输出到终端、日志、仓库或产品数据。
- 允许受保护的本地 OpenCLI 运行时在本机短暂处理页面/网络数据；对外只报告脱敏布尔结果和计数。
- 任意登录、权限、频道身份、网络新鲜度或游标异常立即停止；不得尝试规避限制、切换直接接口、导出认证材料或无限重试。

## 3. 最小测试路径

1. `opencli doctor` 验证 Browser Bridge 健康；绑定用户已经打开的目标标签。
2. 只读识别消息虚拟列表的候选滚动父容器，记录其初始滚动度量，但不输出 DOM 文本或身份信息。
3. 对该容器执行一次向历史方向的受控滚动；等待 Discord 页面完成可能的消息加载。
4. 仅在内存中比较滚动前后度量与新网络响应的脱敏边界：是否移动、是否出现新的匹配历史响应、该响应的最旧消息边界是否比前一响应更早。
5. 最多重复一次。任一失败即停止，不进行适配器修复或扩大测试。

## 4. Go / No-Go

只有同时满足以下条件才为 `Go`：

1. 两次滚动均改变指定消息容器的历史方向位置；
2. 每次后均获得一条新鲜、频道匹配的 Discord 历史消息响应；
3. 第二条响应的最旧消息边界严格早于第一条；
4. 终端输出、Git diff、trace 与工程文档均未泄漏真实内容或认证材料。

任一条件不满足即为 `No-Go`。`No-Go` 只表示当前 OpenCLI/Discord 交互组合不能提供可靠容器翻页能力；不把“无响应”解释为频道没有消息。

## 5. 后续边界

`Go` 只授权提出下一份独立 Spec：讨论高水位锚点、500 条执行上限、断点恢复、去重和真实授权验收。它不授权这些实现，更不授权生产自动化。`No-Go` 时继续维持当前 Discord 收口决定，Bot 授权仍是正式候选路线。
