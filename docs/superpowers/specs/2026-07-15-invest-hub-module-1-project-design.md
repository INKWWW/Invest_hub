## 1. 产品目标与问题本质

Invest Hub 面向个人及少量受邀用户，是一个持续沉淀外部投研信息、个人判断、交易策略和复盘结果的投资信息与投资决策工作台。

本项目只覆盖模块 1「投资信息收集」。模块 2「选股研判」、模块 3「策略和复盘」和模块 4「投资体系」不属于当前项目范围。

模块 1 的本质不是简单搬运 Discord 和 X 内容，而是建立一条长期可运行的事实加工链路：

外部信息

→ 增量采集

→ 原始事实保存

→ 确定性处理

→ LLM 结构化理解

→ 批次总结

→ 日累计总结

→ 网页阅读与证据回溯

系统必须能够回答：

- 这条事实来自哪里；
- 谁在什么时间表达了什么；
- 这条摘要引用了哪些原始内容；
- 哪些内容是事实、发言者观点、系统归纳或不确定判断；
- 采集失败后从哪里恢复；
- 摘要是否基于实际采集内容，而不是模型臆测。

## 2. 项目级决策

本轮已确认：

- 项目 spec 采用总 spec 形式，覆盖完整模块 1 的产品与技术边界；
- Spike-01、Spike-02、V0、V1、V2、V3 保持独立子项目；
- V1 Discord 正式可用定义为 MVP；
- 当前路线以 Codex CLI 作为唯一真实 LLM Provider 候选，Mock 仅用于确定性测试；不纳入 GLM API 或自动 fallback；
- Discord 后续采集路线以 OpenCLI Browser Bridge + 项目侧 Active Adapter 作为未来 V0 的候选主路径；原始 OpenCLI Connector 保留为诊断基线和必要时的回退候选；该路线仍需在 V0 Spec/Plan 中确认，不等于当前生产批准；
- MVP 包含管理员、邀请码和受邀普通用户；
- V1 支持多个 Discord 频道、全局指定用户和频道级覆盖；
- MVP 质量采用“安全门槛硬性化、性能指标暂定”；
- 运行架构采用云端控制面 + 用户本地 Worker；
- 项目采用证据门禁式分阶段推进；
- 真实网页、私有数据、Cookie、Chrome Profile 和密钥不得进入 Git 或云端；
- 未经 Spike/V0 验证的候选技术不视为最终技术栈。

## 3. 产品范围

### 3.1 MVP：V1 Discord 正式可用

V1 是第一个可日常使用的产品版本，至少包含：

- 多个 Discord 频道；
- 全局指定用户；
- 频道级新增、停用和排除覆盖；
- 每个来源独立 checkpoint；
- Discord 增量采集；
- 离线补采；
- 批次总结；
- 每次运行后的日累计总结；
- 原始消息证据回溯；
- 管理员配置中心；
- 管理员任务控制；
- 管理员、邀请码和普通用户权限隔离；
- Codex CLI、Mock Provider；
- Codex CLI 失败后保留失败状态、局部重试和恢复入口；不自动切换到 GLM 或其他外部 Provider；
- Prompt 版本和实际 Provider 记录；
- 桌面端和手机端阅读；
- 任务状态、简化错误和局部重试。

V1 不要求跨频道话题聚合，不要求跨天观点历史追踪，也不要求长期 Topic Memory。

### 3.2 后续版本

V2 在 V1 基础上增加：

- X 博主配置；
- 原创、引用、回复和普通转发；
- 中文摘要；
- 外部文章卡片信息；
- 媒体未解析标记；
- 按自然日和博主阅读；
- X 独立 checkpoint 和任务隔离。

V3 负责：

- Discord 和 X 体验统一；
- 配置中心和任务状态完善；
- 365 天原始数据清理；
- 90 天技术日志清理；
- 生产配置、部署、安装、更新、状态检查和卸载文档；
- 全系统回归、安全和容量验收；
- 升级与回滚路径。

## 4. 用户、权限与数据空间

### 4.1 管理员

管理员可以：

- 查看全部已生成内容；
- 管理 Discord 频道；
- 管理 Discord 指定用户；
- 管理 X 指定博主；
- 生成、停用和管理邀请码；
- 手动触发 Discord 或 X 更新；
- 查看任务状态和简化错误；
- 手动重试失败任务；
- 编辑、测试和启用 Prompt；
- 查看和切换 LLM Provider；
- 查看 Worker 心跳和运行信息。

### 4.2 普通用户

普通用户可以：

- 使用邀请码注册；
- 登录后查看全部已生成内容；
- 查看 Discord 总结、批次和原始消息；
- 查看 X 总结与原始链接；
- 展开历史版本和证据。

普通用户不能：

- 进入配置中心；
- 手动触发更新；
- 查看完整技术日志；
- 修改 Prompt 或 Provider；
- 管理邀请码和信息源。

### 4.3 共享数据空间

所有用户共享同一套已生成数据。

V1 不支持：

- 用户独立信息源；
- 用户独立数据空间；
- 已读未读；
- 未读数量；
- 服务端阅读进度。

## 5. 核心业务流程

### 5.1 管理员配置

1. 管理员登录控制面。
2. 配置 Discord 频道、全局指定用户和频道级覆盖。
3. 配置 X 博主、Prompt 和 LLM Provider。
4. 生成或停用邀请码。
5. 查看 Worker 心跳、任务状态和简化错误。
6. 手动触发任务或等待北京时间 08:00、20:50 的自动任务。
7. 对失败任务执行局部重试。

管理员配置变更先进入待验证或待执行状态，不直接假定来源可用。

### 5.2 Worker 执行

1. 本地 Worker 启动并上报心跳。
2. 拉取可执行任务和已启用来源配置。
3. 复用专用 Chrome Profile，通过 OpenCLI Browser Bridge 和项目侧 Discord Active Adapter 读取网页。
4. 根据来源 checkpoint 增量采集。
5. 完成规则处理、动态分块、结构化分析和批次总结。
6. 原始数据和结果成功持久化后推进 checkpoint。
7. Discord 批次完成后生成或更新当天日累计总结。
8. 上报任务状态、实际 Provider、覆盖范围和错误。
9. Worker 离线恢复后继续未完成任务。

### 5.3 普通用户阅读

1. 使用邀请码注册并登录。
2. 默认进入 Discord 页面。
3. 查看当前自然日的日累计总结和批次总结。
4. 按频道和日期切换。
5. 展开原始消息、原始链接和历史摘要版本。
6. 查看 X 页面中的博主摘要和原始链接。

当前自然日无任何批次和任务时，页面回退到最近有数据的日期。

## 6. 总体架构

项目采用云端控制面 + 本地执行面的双平面架构。

### 6.1 云端控制面

云端负责：

- 登录、邀请码和角色权限；
- 来源、指定用户、Prompt 和 Provider 配置；
- 任务创建、状态查询和重试入口；
- Worker 注册、心跳和任务领取；
- 原始数据、结构化结果、摘要版本和证据索引；
- Discord/X 阅读页面；
- 日累计总结和历史版本；
- 数据清理和运行元信息。

云端不保存用户 Chrome Profile、Cookie 或网页登录凭据。

### 6.2 本地执行面

本地 Worker 负责：

- 专用 Chrome Profile；
- OpenCLI Runtime；
- Discord Connector 和 X Connector；
- Discord Active Adapter（V0 候选主路径）；
- checkpoint 增量采集；
- 规则处理和动态分块；
- LLM Provider 调用；
- JSON Schema 校验；
- 局部重试和失败恢复记录，不自动切换到未验证的其他 Provider；
- 结果上传和任务状态回报；
- 本地日志和心跳。

真实网页状态必须留在用户控制的本地执行面。

### 6.3 业务隔离链路

所有来源统一经过：

来源原始输出

→ Discord/X Connector

→ Invest Hub Canonical Schema

→ 确定性处理

→ LLM 结构化结果

→ 批次和日累计摘要

→ 阅读与证据回溯

业务逻辑不得直接依赖 OpenCLI、Discord DOM、X 页面结构或某个 Provider 的原始输出。

### 6.4 技术选型边界

intake 中的 Next.js、TypeScript、Vercel、Supabase 及任务机制是候选方向，不是已批准的最终技术栈。

最终技术选型必须经过 Spike-01、Spike-02 和 V0 验证，并记录在相应正式 spec 或 implementation plan 中。项目总 spec 只固定逻辑架构、信任边界、数据原则和恢复原则。

## 7. 组件边界

### 7.1 身份与权限

负责登录、邀请码、角色和共享数据权限；不负责来源采集和任务执行。

### 7.2 来源配置

负责 Discord 频道、指定用户、X 博主、启停和验证状态；不负责读取网页和推进 checkpoint。

### 7.3 任务控制

负责定时/手动任务、任务状态、租约、来源隔离和重试入口；不负责页面采集和 LLM 内容理解。

### 7.4 本地 Worker

负责心跳、任务领取、浏览器会话、OpenCLI、Connector 调度和结果回报；不负责普通用户权限决策。

### 7.5 来源 Connector

负责来源特有页面解析和原始输出转换；不负责摘要、跨来源聚合或投资判断。

### 7.6 Canonical Schema

负责统一来源、消息/帖子、作者、时间、关系、附件和证据字段；不负责摘要和 UI 排版。

### 7.7 确定性处理

负责去重、作者识别、回复还原、时间排序、ticker/URL 提取、动态分块、Top N、字段补齐和 Schema 校验；不负责观点判断。

### 7.8 Provider Gateway

负责 Codex CLI、Mock 的统一接口、重试、健康状态和实际 Provider 记录；不负责直接访问来源网页，也不负责自动切换到未验证的外部 Provider。

### 7.9 总结流水线

负责 chunk 分析、程序聚合、批次总结、日累计总结、版本和证据映射；不修改原始事实。

### 7.10 数据、证据和清理

负责原始内容、结构化结果、摘要版本、证据索引、日志和保留期限；不决定摘要内容。

### 7.11 阅读与配置界面

负责内容优先展示、日期/频道/博主切换、管理员配置和任务状态；不直接执行本地浏览器采集。

## 8. 数据模型与数据流原则

### 8.1 最小统一数据能力

模块 1 的数据结构必须为后续模块保留：

- 来源；
- 作者；
- 标的；
- 时间；
- 观点；
- 操作倾向；
- 原始证据；
- 摘要版本；
- 内容类型；
- 回复、引用和上下文关系。

最终 Canonical Schema、统一表或分表由 Spike/V0/V1 的独立 spec 确认。

### 8.2 数据流

1. 管理员配置来源。
2. Worker 验证访问权限并建立初始 checkpoint。
3. 定时或手动任务读取来源 checkpoint。
4. Connector 采集原始内容。
5. 原始内容先被持久化。
6. 记录进入 Canonical Schema。
7. 确定性程序去重、还原关系、提取字段并动态分块。
8. Provider 生成结构化结果。
9. 程序聚合并校验批次结果。
10. 生成批次摘要和日累计摘要。
11. 发布最新版本并建立证据映射。
12. 原始数据保存成功后推进 checkpoint。

### 8.3 一致性不变量

- 原始事实、结构化结果和摘要版本分层保存；
- checkpoint 只能在成功持久化后推进；
- 失败不能通过跳过未确认范围制造成功；
- 外部 ID 是来源级幂等基础；
- 回复和引用目标缺失时保留 unresolved 状态；
- 摘要版本不可变，重新生成产生新版本；
- 日累计总结从当天已成功批次结构化结果重新生成，不直接续写旧文本；
- 每条摘要可以在原始数据保留期内回溯到证据。

### 8.4 来源处理差异

Discord：

- 批次总结按频道独立生成；
- 指定用户观点、操作倾向和投资方法只统计指定用户；
- 核心讨论、标的、情绪和其他讨论统计全频道；
- 每个频道每个运行批次更新日累计总结。

X：

- 原创、引用、回复和普通转发必须保留内容类型；
- 引用内容与博主附加评论分开；
- 回复保留被回复上下文；
- 无附加评论转发不得表述为明确认同；
- 外部文章只保留页面可见卡片信息，不读取正文；
- 不做跨博主综合总结。

## 9. 内容处理与摘要规则

### 9.1 确定性程序

程序负责：

- 去重；
- 系统消息、纯表情和无关内容的规则处理；
- 回复关系还原；
- 作者和指定用户识别；
- ticker、价格、百分比和 URL 提取；
- 时间排序；
- 动态分块；
- Top 5 截取；
- 消息 ID 和证据存在性校验；
- JSON Schema 校验；
- 重复话题初筛；
- 相同 ticker 候选合并；
- 缺省字段补齐。

### 9.2 LLM

LLM 只负责：

- 语义分类；
- 话题识别；
- 局部提炼；
- 结构化总结；
- 批次和日累计总结所需的语言表达。

LLM 不得臆测未解析的图片、PDF、表格、视频、语音或外部文章正文。

### 9.3 Discord 摘要

批次总结固定栏目：

1. 重点人物观点；
2. 核心讨论；
3. 涉及标的；
4. 操作倾向；
5. 市场情绪；
6. 投资方法与心态；
7. 其他重要讨论。

核心讨论最多展示 5 个话题，其他重要讨论不设固定条数但必须高度压缩。

日累计总结固定关注：

1. 全天核心结论；
2. 指定用户观点变化；
3. 群聊整体变化；
4. 重点风险和待跟踪事项。

### 9.4 X 摘要

每个博主每个运行批次独立总结，固定栏目：

1. 核心观点；
2. 涉及标的；
3. 操作倾向；
4. 引用与转发内容；
5. 态度变化；
6. 其他重要内容。

X 摘要统一使用中文，同时保留原文、ticker、公司名、ETF、缩写和专业词汇。

## 10. 失败处理与恢复

### 10.1 来源和浏览器

登录态失效、无权限、页面结构变化、虚拟滚动失败、网络超时或限流时：

- 进行来源级局部重试；
- 网络和限流采用指数退避；
- 单来源失败不阻断其他来源；
- 进入可重试状态；
- 不把访问失败当成空数据；
- 完整诊断后台保存，用户端展示简化错误。

### 10.2 Worker 与任务

- Worker 离线不视为永久失败；
- 恢复后继续未完成任务；
- 任务租约过期后允许安全接管；
- 已完成 chunk 不重复处理；
- 单个任务恢复不影响其他来源。

### 10.3 LLM 与 Provider

- 超时和限流：指数退避；
- 输出截断：缩小或拆分 chunk；
- JSON 错误：程序修复或短格式修复请求；
- 单 chunk 失败：只重试该 chunk；
- Codex CLI 连续失败：保留失败状态、输入范围和诊断，按任务策略恢复或人工处理；
- Codex 也失败：保留失败状态和输入范围；
- 每次执行记录 Provider、Prompt 版本、耗时和重试次数。

### 10.4 摘要和版本

采集成功但摘要失败时：

- 原始数据和已完成结构化结果继续保留；
- 日累计总结保持上一成功版本；
- 页面标记存在未完成批次；
- 重试成功后生成新的完整版本；
- 不覆盖旧的成功版本。

### 10.5 内容不确定性

- 未解析媒体必须明确标记；
- 核心信息依赖未解析附件或文章正文时，不生成确定性结论；
- 回复或引用目标缺失时保留 unresolved 状态；
- 普通转发不得被错误归因于作者明确观点。

## 11. 安全、隐私和数据治理

### 11.1 来源访问

只采集用户本人已加入、已付费或有权限访问，且在已登录网页中正常可见的 Discord 频道和指定 X 博主内容。

专用浏览器 Profile 不得登录邮箱、金融账户或其他无关账号。

### 11.2 权限

- 管理员配置、任务和完整日志仅管理员可见；
- 普通用户只能阅读共享数据和证据；
- 服务端权限和数据库级隔离共同保证访问边界；
- Worker 只能领取授权范围内的任务。

### 11.3 敏感信息

不得进入 Git 或普通日志：

- Supabase、Codex 等密钥；
- Cookie、Token、密码和 Chrome Profile；
- 私有频道、博主名单和邀请码；
- 私有 Prompt；
- 真实 fixture 和历史数据；
- 未经处理的真实消息正文和完整附件链接。

仓库只保留通用代码、公开人工 fixture 和环境变量模板。

### 11.4 保留期限

- Discord/X 原始内容：365 天；
- 结构化结果、摘要和摘要版本：长期；
- 技术日志：90 天；
- 原始数据清理后不保留作者、时间、链接或原文摘录快照；
- 旧摘要继续保留，但失效证据入口必须明确标记。

## 12. 阅读与配置体验

### 12.1 导航

V1 只展示：

- Discord 信息；
- X 信息；
- 管理员任务状态；
- 管理员配置中心。

模块 2—4 不显示“开发中”占位。

### 12.2 Discord 页面

桌面端使用左侧频道列表和主内容区；手机端使用顶部频道选择和单列卡片。

阅读层级为：

自然日

→ 日累计总结

→ 当天运行批次

→ 原始消息和历史版本

内容优先，运行状态、生成时间、覆盖范围和 Provider 等元信息后置；处理中、部分失败和失败状态提升到标题附近。

### 12.3 X 页面

按自然日展示：

自然日

→ 博主

→ 最新摘要

→ 原始链接

每个博主默认完整展开；历史版本默认折叠；不做统一跨博主时间线。

### 12.4 视觉与移动端

整体风格简约、阅读优先、护眼、信息清晰，避免投资数据大屏式三栏布局。

手机端必须支持日期/来源切换、日累计总结、批次总结、原始证据、原始链接和历史版本。配置中心可简化但不能完全不可用。

## 13. 测试与验收

### 13.1 测试数据

- 仓库只保留人工构造公开 fixture；
- 真实内容即使脱敏也只在本地保存；
- fixture 保留顺序、回复关系、观点关系、ticker 和多语言特征；
- 真实网页测试用于验证 OpenCLI、登录态和页面行为。

### 13.2 确定性测试

必须自动化验证：

- 登录、邀请码、角色权限和 RLS；
- Worker 心跳、任务租约和恢复；
- checkpoint、去重和幂等；
- 消息/帖子身份和内容类型；
- 回复、引用和原始链接；
- Canonical Schema；
- chunk 局部重试；
- Provider 和 Prompt 版本记录；
- 日累计摘要版本；
- 原始数据和日志清理。

### 13.3 概率性质量测试

使用固定 fixture 和人工标注检查：

- 指定用户观点；
- 操作倾向；
- ticker 和标的；
- 群聊整体变化；
- 指定用户观点变化；
- 核心观点证据；
- 错误归因；
- 媒体和外部文章臆测；
- 中文表达；
- 重复和空泛内容。

不要求摘要逐字一致，而要求事实、归因、证据和关键内容满足门槛。

### 13.4 真实网页测试

至少覆盖：

- Discord 1000 条以上多页采集；
- X 四类帖子；
- 登录态复用；
- 分页或虚拟滚动；
- 回复、引用和附件元数据；
- 二次运行不重复；
- Worker 离线补采；
- Mac 重启后的恢复。

### 13.5 硬性门槛

- 严重错误归因：0；
- 未解析媒体臆测：0；
- 权限越界：0；
- checkpoint 越界：0；
- 关键证据无法回溯：0；
- 阻断级恢复测试失败：不通过。

采集完整率、LLM 成功率、JSON 合法率和 P95 响应时间作为初始目标，待 Spike-01 和 Spike-02 后校准。

### 14.1 Discovery

产出项目总 spec、Spike-01/02 spec 和 plan，确认 MVP、非目标、风险和未决项。本阶段不生成应用代码、框架或生产依赖。

### 14.2 Spike-01

docs/superpowers/specs/2026-07-15-spike-01-opencli-discord-incremental-design.md

### 14.3 Spike-02

验证 Codex CLI 容量和质量、动态分块、JSON 稳定性和 Codex CLI 无人值守运行。

### 14.4 V0

只有在两个 Spike 结论可用后，才确定控制面、Worker、任务、权限、Provider 和 OpenCLI 的正式实现边界。V0 Discord 抓取 Spec 应以 Active Adapter 作为候选主路径，明确其与原始 OpenCLI Connector 诊断基线/回退候选的关系，并把会话健康检查、freshness、有限重试、截止时间、逐页 telemetry 和 checkpoint 恢复写入验收标准；这仍不授权当前开始 V0 实现。

### 14.5 V1、V2、V3

每个版本都有独立 spec、独立 implementation plan、独立测试门禁和退出条件。一个版本未通过阻断级验收，不进入下一个版本。

## 15. 未决事项

- Worker 认证、任务租约和恢复细节；
- Codex CLI 的实际容量、限流和成本；
- 未来如引入其他 Provider 时的独立验证和切换规则；
- 动态分块的安全输入、输出和重叠参数；
- Prompt 测试、启用和回滚流程；
- 日累计总结的输入上限；
- 页面长列表、分页和历史版本交互；
- 数据清理任务的具体执行方式；
- 最终云端、数据库和任务系统技术选型。

这些是有意保留的决策门，不是实现遗漏。

## 16. 项目成功定义

模块 1 成功不等于“网页能够展示 Discord 和 X 内容”，而是：

- 能长期稳定采集；
- 电脑离线后能补采；
- 原始数据不丢失；
- 指定用户和博主观点不错误归因；
- Codex CLI 失败时可以局部重试、恢复或明确记录失败状态；
- 高消息量下任务最终可完成；
- 日累计总结突出核心点和观点变化；
- 用户可以从自然日和批次快速阅读；
- 用户需要时可以追溯到原始消息和原始链接；
- 系统具备明确测试门禁、日志、恢复和后续扩展能力。

## 17. Spec 自检

- 范围检查：只覆盖模块 1，明确排除模块 2—4。
- MVP 检查：V1 Discord 正式可用已明确为 MVP；V0、V2、V3 的角色已区分。
- intake 约束检查：事实优先、内容优先、可追溯、增量处理、低成本、可迁移和安全边界均已保留。
- 决策边界检查：候选技术栈没有被写成最终选型；Spike/V0 仍保留技术验证责任。
- 架构一致性检查：云端控制面不持有浏览器登录态，本地 Worker 执行网页采集和 Provider 任务。
- 数据一致性检查：原始保存先于 checkpoint 推进；摘要版本不可变；证据映射保留。
- 故障覆盖检查：来源、Worker、持久化、LLM、摘要和内容不确定性均有处理规则。
- 安全检查：密钥、Cookie、Profile、私有来源、真实 fixture 和历史数据均不得进入 Git 或云端。
- 测试检查：确定性、概率性、真实网页、恢复、权限、清理和阶段门禁均有覆盖。
- 占位符检查：没有待办项、未决占位或模糊的实现占位。

自检结论：项目总 spec 的范围、MVP、架构边界、版本路线和未决事项相互一致；本文不授权生产实现，也不替代后续子项目 spec 和 implementation plan。
