# Spike-01：OpenCLI Discord Web 增量采集设计

## 文档状态

- 阶段：Discovery / Spike 设计
- 书面状态：Revision-01 已批准
- 本文范围：只设计 Spike-01，不授权生产实现
- 设计依据：AGENTS.md、docs/project-status.md、docs/intake.md
- 已确认的对话决策：产品范围、双轨证据、硬性字段、严格 OpenCLI 判定、方案 B，以及以下各设计分段均已获得用户批准
- Revision-01 原因：222 条真实消息的证据写入窗口约 93 秒，但之前一次运行的墙钟时间接近 2 小时；现有 harness 没有记录逐页耗时，无法区分正常采集、网络响应等待、陈旧响应、OpenCLI 子进程超时和外部交互等待。
- Revision-01 原则：1000 条仍是必须由采集器真实获取的完整性验收目标；人工导出、人工提供 1000 条数据或固定依赖某个未经验证的响应等待参数，均不能替代验收。

## 1. 目标与第一性原理

Spike-01 只回答一个问题：

> 在用户本人已登录且有权限访问的 Discord Web 私有频道中，OpenCLI 是否能稳定、增量、可追溯地采集后续 V1 所需的消息数据？

问题的本质不是“能否从页面抓到一些文本”，而是能否建立一个可信的增量事实入口。可信入口必须同时满足：

1. 每条消息有稳定身份；
2. 作者、频道、时间和正文可归属；
3. 回复、引用和附件等上下文关系不被静默丢失；
4. 重复运行不会重复入库；
5. 中断恢复不会越过尚未成功保存的数据；
6. 失败可以定位，结果可以审计；
7. 真实网页能力与确定性增量逻辑可以分开验证。

本 Spike 不实现产品，只建立是否继续 OpenCLI-first 的证据基础。

## 2. 范围与非目标

### 2.1 MVP 范围

采用双轨验证：

1. 真实网页轨：使用本地专用 Chrome Profile，验证一个真实私有频道，至少连续读取 1000 条消息。
2. 确定性验证轨：使用公开人工 fixture 和 Fake Connector，验证 checkpoint、幂等、断点恢复、失败隔离和缺口处理。

真实网页轨的 1000 条必须由 OpenCLI 采集链路从 Discord 页面实际取得。人工导出只可作为故障分析时的外部对照资料，不能作为输入 fixture、不能计入消息数量，也不能证明采集器完整。

真实网页轨必须验证：

- 消息唯一 ID；
- 作者唯一 ID和显示名；
- 频道标识；
- 发布时间；
- 正文；
- 回复关系；
- 引用目标或引用内容；
- 附件元数据和链接；
- 二次运行不重复；
- 结果可转换为最小 Canonical Schema。

确定性验证轨必须满足：

- 数据完整率 100%；
- 重复率 0%；
- checkpoint 不越过未成功持久化的数据；
- 中途失败后可继续；
- 单频道失败不阻断其他频道；
- checkpoint 对应消息被删除时有明确容错结论。

### 2.2 严格通过规则

以下任一情况发生，均判定 OpenCLI-first 未通过：

- 任一硬性字段无法稳定获取；
- 回复、引用或附件关系无法达到可接受的可靠性；
- 1000 条以上采集无法完成；
- 二次运行产生重复或明显缺口；
- OpenCLI 输出无法稳定转换为最小 Canonical Schema；
- 只能依靠 Playwright/CDP 才能补齐硬性字段。

Playwright/CDP 可以作为诊断工具，但其结果不能算作 OpenCLI 通过。

### 2.3 明确不做

本 Spike 不包含：

- 生产应用代码；
- 云端数据库、认证、邀请码和 RLS；
- Worker 生产任务系统；
- 正式 checkpoint 服务；
- LLM、清洗、分类、摘要和网页阅读页；
- X 采集；
- 完整 OpenCLI 私有 Adapter；
- Playwright/CDP 后备采集器；
- 生产依赖安装；
- 真实 Cookie、Chrome Profile、频道信息或历史数据入 Git。

## 3. 方案比较与选型

### 3.1 方案 A：直接使用 OpenCLI 黑盒输出

用现有 OpenCLI Discord 能力采集消息，再对输出做一次性字段检查和人工核验。

优点是最快、最接近真实使用方式。缺点是无法验证业务边界，OpenCLI 原始输出会直接影响后续设计，失败时也难以定位是采集、转换还是 checkpoint 问题。

### 3.2 方案 B：OpenCLI + Canonical Schema 合约验证器

设计一次性的 Spike 验证 harness，形成：

OpenCLI 原始输出 → Discord 适配边界 → 最小 Canonical Schema → 字段与关系校验 → checkpoint 模拟 → 证据报告

同时使用 Fake Connector 和公开 fixture 验证幂等、断点恢复、失败隔离等确定性行为。

该 harness 只用于验证边界，不是生产代码。是否将接口和模型正式纳入后续 V0/V1，须根据 Spike 结果另行批准。

优点是可以分别判断 OpenCLI 能力、适配边界和增量逻辑；失败可定位；结果可直接支撑后续 Spec。代价是设计和验证工作量略高，需要定义最小 Canonical Schema。

### 3.3 方案 C：OpenCLI 原始能力 + 诊断探针

以 OpenCLI 为主，同时设计 DOM/网络数据的只读诊断探针，用于解释字段缺失、虚拟滚动、回复关系和分页行为。

探针只能帮助诊断，不能把 Playwright/CDP 结果算作 OpenCLI 通过，也不能建设第二套完整采集方案。

该方案诊断能力最强，但容易扩大 Spike 范围。因此只在方案 B 发现无法解释的缺口时按需使用。

### 3.4 选定方案

采用方案 B，有限吸收方案 C 的诊断能力。方案 A 不作为正式设计，因为它无法证明后续业务边界和恢复语义。

### 3.5 Revision-01：可观测的响应获取策略

本次真实运行已经证明：成功获取并保存页面后，单页数据处理很快；主要风险集中在“页面已导航，但目标消息响应尚未被 OpenCLI network 观察到，或观察到的是旧响应”的长尾等待。因此本 Spike 不把固定等待时间视为最终方案，而增加一个可替换的响应获取边界：

1. 每个页面必须记录安全的阶段耗时：导航、等待、network 观察、响应 detail、映射、验证和持久化。
2. 每次 network 观察必须记录尝试次数、响应匹配状态和失败分类，但不得把正文、频道 URL、Profile 路径、Cookie 或 Token 写入遥测。
3. 响应匹配必须同时验证目标频道和当前分页 cursor；无法证明响应是本次分页的新响应时，必须标记为 stale/ambiguous，不得当作成功页面。
4. 每页设置硬性操作截止时间，避免单个页面无限重试；超时后保留已完成证据和旧 checkpoint，并返回可恢复的 partial 结果。Implementation Plan 的 90 秒是运行保护默认值，不是“90 秒内完成页面”的性能通过标准。
5. 在正式 1000 条运行前，先做 100–200 条有遥测的 bounded soak。该阶段只用于定位时间分布，不降低 1000 条验收，也不允许以 soak 结果宣布通过。
6. 如果 bounded soak 证明 network 观察仍存在不可接受的缺失或陈旧响应长尾，再比较 OpenCLI 的定向 XHR 等待、重新触发分页请求或 Discord Desktop 局部 Spike；不得直接切换到人工导出或未批准的第二套采集框架。

当前结论只批准“先增加遥测并验证响应策略”，不批准某个具体 OpenCLI 等待命令、Discord Desktop 路线或生产采集架构。

## 4. 操作流程

Spike 只面向一名本地测试操作者，不引入管理员、普通用户或正式网页流程。

### 4.1 前置准备

1. 操作者在专用 Chrome Profile 中登录 Discord。
2. 操作者提供一个已确认有权限访问的频道 URL。
3. 测试配置只保存在本地。
4. 采集过程必须是只读操作，不发送消息、不修改频道内容、不操作无关账号。

### 4.2 真实网页验证流程

1. 验证专用 Profile 是否仍处于有效登录状态。
2. 打开指定频道并确认可访问。
3. 从频道当前可见位置开始采集，不回溯到启用前历史范围之外。
4. 持续读取分页或虚拟滚动内容，直到达到 1000 条以上或明确遇到 OpenCLI 能力边界。
5. 对每条结果提取并验证已批准的硬性字段。
6. 保存 OpenCLI 原始输出的本地诊断副本。
7. 转换为最小 Canonical Schema。
8. 执行字段、关系和来源链接校验。
9. 使用同一 checkpoint 再运行一次，验证不会重复采集。
10. 记录采集数量、缺失字段、重复、缺口、耗时和失败位置。
11. 在正式 1000 条运行前，先完成 100–200 条 bounded soak，并确认每页都有阶段耗时和响应匹配状态。
12. 只有 bounded soak 的失败原因可解释、可恢复且没有无界等待时，才开始 1000 条真实验收。

### 4.3 确定性恢复验证流程

1. 使用 Fake Connector 注入连续消息、回复、引用、附件和跨页数据。
2. 首次运行只成功持久化部分数据。
3. 模拟 Worker 或采集过程崩溃。
4. 重新运行，从最后一个成功持久化位置继续。
5. 验证不重复、不漏采，且 checkpoint 不越过未成功数据。
6. 准备两个独立频道，其中一个注入失败，验证另一个仍可完成。
7. 模拟 checkpoint 对应消息已被删除，记录可恢复范围和不可恢复边界。

### 4.4 结束条件

Spike 在以下任一条件满足时结束：

- 所有硬性验收项完成并形成通过结论；
- 任一硬性验收项失败，并形成不通过结论；
- 真实网页条件不足，无法继续验证，并明确标记为“未验证”，不得推断为通过。

失败时不自动切换到 Playwright/CDP，也不继续扩大采集范围。

## 5. 系统架构与组件边界

Spike 采用真实网页轨和确定性 fixture 轨共用同一条验证后半链路：

Connector → Canonical Schema → Validator → Checkpoint/Idempotency → Evidence Report

### 5.1 Spike Runner

负责：

- 启动一次真实轨或 fixture 轨测试；
- 注入测试配置；
- 管理运行批次和停止条件；
- 汇总各组件结果；
- 不承载 Discord 业务规则。

### 5.2 OpenCLI Boundary

负责：

- 调用已锁定版本的 OpenCLI；
- 复用本地专用 Chrome Profile；
- 获取 Discord 页面数据；
- 返回原始采集结果和运行诊断信息。

边界要求：

- Spike 业务逻辑不得直接依赖 OpenCLI 原始字段；
- OpenCLI 版本、登录态和浏览器环境作为外部依赖记录；
- 不读取、导出或持久化 Cookie 和凭据。
- 对每页输出不含敏感内容的阶段遥测和响应匹配状态；遥测不能代替原始证据，也不能把未经确认的旧响应标记为成功。
- 响应获取机制必须保持可替换，不能把一次 Spike 运行中验证不足的固定等待时长固化为产品承诺。

### 5.3 Discord Connector Adapter

负责：

- 将 OpenCLI 原始输出转换为 Discord 中间记录；
- 保留原始消息与原始字段；
- 提取作者、频道、时间、正文、回复、引用和附件信息；
- 对字段缺失进行显式标记；
- 不负责 checkpoint 决策。

Fake Connector 必须输出同一类中间记录，使真实轨和 fixture 轨能够共用后续验证逻辑。

### 5.4 Canonical Schema Mapper

负责：

- 将 Discord 中间记录映射到统一消息记录；
- 保留来源类型、来源容器、外部消息 ID、作者、时间、正文、上下文、附件、来源链接和采集时间；
- 不做摘要、分类或投资判断；
- 不丢弃无法解析的原始字段。

这是 Spike 草案，不固化 V1 最终表结构。

### 5.5 Validator

负责：

- 校验必填字段；
- 校验消息 ID、作者 ID和频道 ID的一致性；
- 校验时间顺序；
- 校验回复和引用目标；
- 校验附件元数据；
- 校验 Canonical Schema；
- 输出缺失、冲突、重复和疑似漏采结果。

### 5.6 Checkpoint Emulator

负责：

- 模拟成功持久化后的 checkpoint；
- 验证重复运行；
- 验证中断恢复；
- 验证 checkpoint 不越过未成功数据；
- 验证多频道相互隔离。

它是 Spike 的本地验证组件，不代表 V0/V1 的最终 checkpoint 实现。

### 5.7 Evidence Recorder

负责保存：

- 测试配置摘要；
- OpenCLI 版本；
- 运行批次；
- 原始输出索引；
- Canonical Schema 样本；
- checkpoint 变化；
- 验证指标；
- 失败位置和错误分类；
- 最终通过/不通过结论。

真实数据只写入本地受保护目录，不进入 Git。

### 5.8 组件依赖原则

- OpenCLI 只负责浏览器采集；
- Connector 只负责来源适配；
- Canonical Schema 负责业务隔离；
- Validator 负责可验证性；
- Checkpoint Emulator 负责增量行为；
- Evidence Recorder 负责可审计性；
- 任何组件都不负责 LLM、摘要、用户权限或生产任务调度。

## 6. 最小 Canonical Schema 草案

Schema 只用于 Spike 合约验证，最终字段和表结构由后续正式 Spec 决定。

每条消息至少包含：

- source_type：固定为 Discord；
- source_account_id：本地测试账号的非敏感标识或脱敏标识；
- source_container_id：频道唯一标识；
- external_item_id：Discord 消息唯一标识；
- author_id：Discord 用户唯一标识；
- author_name：当前显示名；
- published_at：Discord 原始发布时间；
- content_text：正文，可为空但必须有明确原因；
- content_type：文本、系统或其他可辨识类型；
- parent_item_id：回复目标消息 ID，无法解析时为空；
- quoted_item：引用目标的结构化信息或 unresolved 标记；
- attachments：附件元数据和链接；
- source_url：原始消息链接，如可取得；
- raw_payload_ref：本地原始证据引用；
- collected_at：本次采集时间。

Schema 不允许通过推测补齐作者、正文、回复目标或附件内容。

## 7. 数据流与一致性不变量

### 7.1 主数据流

1. Spike Runner 读取本地测试配置和当前 checkpoint。
2. OpenCLI 在专用 Profile 中读取 Discord 页面，产生原始采集结果。
3. Connector Adapter 将原始结果转换为 Discord 中间记录。
4. Canonical Schema Mapper 生成统一消息记录。
5. Validator 执行字段、关系、顺序、重复和来源校验。
6. Evidence Recorder 先保存原始结果、标准化结果和校验结果。
7. Checkpoint Emulator 仅在本批次结果已成功保存后推进 checkpoint。
8. Runner 生成本次运行的指标和结论。

### 7.2 两条轨道的汇合点

- 真实网页轨只负责证明 OpenCLI 能产生足够完整的原始数据；
- fixture 轨负责构造可重复的中断、重试、重复和缺口场景；
- 两条轨道从 Connector 输出之后必须共用 Canonical Schema、Validator 和 Checkpoint Emulator；
- 不能因为 fixture 轨通过，就推断真实网页轨字段完整。

### 7.3 核心不变量

#### 原始数据优先保存

任何无法标准化的原始消息，也必须保留其原始结果和失败原因，不能静默丢弃。

#### Checkpoint 后置推进

Checkpoint 表示：截止该位置之前的采集结果已经拥有可追溯的终态。因此，未完成保存、校验或错误记录前，checkpoint 不得推进。

#### 幂等去重

默认去重键为：

source_type + source_container_id + external_item_id

重复运行时：

- 已存在的消息不重复创建；
- 可记录为 duplicate；
- 不改变原始首次采集证据；
- 不推进到未成功覆盖的位置。

#### 关系可追溯

回复或引用目标如果已采集，则关联到对应消息 ID；如果未采集，则保留外部目标 ID、原始引用信息和 unresolved 标记；不得伪造上下文。

#### 顺序可解释

每条消息同时保留 Discord 原始发布时间、采集时间和本次运行中的顺序位置。不能用采集顺序覆盖原始发布时间。

#### 失败可定位

任何失败至少能定位到运行批次、来源频道、原始消息范围、Connector 或 Validator 阶段，以及 checkpoint 前后状态。

#### 耗时可解释

真实网页轨必须能区分：

- 正常页面采集耗时；
- network 响应尚未出现的等待耗时；
- 找到旧响应或无法确认 cursor 的耗时；
- OpenCLI 子进程启动/连接/超时耗时；
- 映射、验证和持久化耗时。

没有逐页阶段遥测时，真实运行只能标记为“耗时未解释”，不得据此判断网络策略已经稳定。

### 7.4 结果状态

每条记录至少产生一种明确状态：

- accepted；
- duplicate；
- invalid；
- unresolved_relation；
- failed。

状态必须进入证据报告，不用“忽略异常数据”的方式制造完整率。

## 8. 失败处理策略

### 8.1 登录态或访问权限失败

如果 Profile 未登录、登录态过期、频道无权限或 URL 无效：

- 立即停止真实网页轨；
- 不尝试读取其他账号或无关页面；
- 不记录 Cookie、Token 或页面敏感内容；
- 标记为环境前置条件失败，不直接判定 OpenCLI 采集能力失败。

### 8.2 页面读取或分页失败

如果虚拟滚动无法继续、页面加载超时、分页出现空洞或同一位置重复返回：

- 进行有限次数的局部重试；
- 记录页面位置和每次重试结果；
- 记录每次重试属于“无响应”“陈旧响应”“错误频道”“cursor 未推进”还是 OpenCLI 命令失败；
- 重试后仍失败则标记采集窗口不完整；
- 单页超过硬性操作截止时间时立即停止该页，保留旧 checkpoint，不允许继续无界等待；
- checkpoint 不越过未确认的数据范围；
- 如果影响 1000 条或硬性字段验收，则 Spike 不通过。

### 8.3 字段缺失或关系解析失败

如果消息 ID、作者 ID、频道 ID、正文或时间缺失，或回复、引用、附件关系不稳定：

- 保留原始 OpenCLI 输出；
- 记录字段级失败原因；
- 不用推断值补齐；
- 不调用 Playwright/CDP 补齐；
- 任一硬性字段持续失败，判定 OpenCLI-first 不通过。

### 8.4 标准化或 Schema 校验失败

- 保留原始记录和转换错误；
- 区分 OpenCLI 未提供字段与 Adapter 转换错误；
- 如果是验证器或映射设计错误，修正 Spike harness 后重跑；
- 如果 OpenCLI 原始数据本身不足，归类为 OpenCLI 能力缺口。

### 8.5 重复与冲突

- 跨运行重复消息：视为幂等验证结果，不新增 Canonical 记录；
- 同一运行内重复消息：记录为采集器异常；
- 同一消息 ID对应不同正文、作者或时间：记录为数据冲突；
- 冲突无法解释时，阻断通过结论。

### 8.6 测试过程崩溃

真实网页轨保留崩溃前的本地证据，不将未确认结果计入成功范围；重新启动后从最近确认位置继续。

fixture 轨必须主动模拟崩溃，验证恢复后不重复、不漏采；恢复逻辑失败则确定性验收不通过。

### 8.7 结果分类

最终报告将失败分为：

- 环境前置条件失败；
- Spike harness 缺陷；
- OpenCLI 能力缺口；
- 数据完整性失败；
- 可恢复临时故障；
- 未覆盖场景。

只有环境前置条件失败或 harness 缺陷，才允许在修复后重跑；OpenCLI 能力缺口和数据完整性失败必须进入路线决策。

## 9. 安全、隐私与数据治理

### 9.1 浏览器与账号边界

- 只使用用户指定的专用 Chrome Profile；
- 只访问用户明确提供的 Discord 频道；
- 只允许 Discord 相关页面导航；
- 不登录、不访问邮箱、金融账户或其他无关服务；
- 采集过程只读，不发送消息、不修改频道内容。

### 9.2 凭据与登录态

- 不要求用户提供账号密码、Cookie 或 Token；
- OpenCLI 只复用本地浏览器登录态；
- 不复制、不导出、不上传 Chrome Profile；
- 不将登录态写入测试报告、环境变量模板或 Git。

### 9.3 真实数据处理

- 真实消息只写入本地受保护的 Spike 证据目录；
- 不上传云端，不写入 Supabase 或其他远程服务；
- 日志只记录消息 ID、范围、计数和错误类型等必要信息；
- 正文和附件链接默认不进入普通运行日志；
- 真实数据保留到结论完成并经用户审阅，之后可清理；
- 真实数据和脱敏真实 fixture 均不得提交 Git。

### 9.4 公开 fixture

仓库如需保留测试样例，只能使用人工构造的公开 fixture。真实脱敏数据继续视为私有数据，不能因为脱敏就进入仓库。

### 9.5 证据与报告

报告可以包含字段映射、计数和完整率、checkpoint 变化、错误分类、OpenCLI 版本、运行时间和耗时。

报告不得包含 Cookie、Token、密码、Chrome Profile 中的敏感内容、邀请码、私有频道名单、未经处理的真实消息正文、完整附件链接或真实历史数据快照。

### 9.6 安全失败处理

若发现证据目录、日志或 Git 工作区可能包含敏感内容：

1. 立即停止测试；
2. 不提交、不上传；
3. 标记安全阻断；
4. 清理或隔离敏感文件；
5. 清理完成后才能继续。

## 10. 测试与验收策略

### 10.1 环境前置检查

验证：

- 专用 Chrome Profile 可用；
- Discord 登录态有效；
- 指定频道可访问；
- OpenCLI 版本已记录；
- 证据目录不在 Git 跟踪范围；
- 未配置任何云端写入。

前置失败不判定 OpenCLI 能力失败。

### 10.2 Canonical Schema 合约测试

使用公开 fixture 验证：

- 字段映射；
- 消息 ID 唯一性；
- 作者和频道归属；
- 时间排序；
- 回复和引用关系；
- 附件元数据；
- 来源链接；
- 缺失字段和 unresolved 状态。

### 10.3 增量与恢复测试

使用 Fake Connector 验证：

- 首次运行；
- 二次运行；
- 重复输入；
- 中途崩溃；
- 从 checkpoint 继续；
- checkpoint 不越过未成功数据；
- 多频道独立失败；
- checkpoint 对应消息被删除；
- 1000 条以上多页数据。

确定性门槛：

- 数据完整率 100%；
- 重复率 0%；
- 失败恢复后最终结果与一次性成功结果一致；
- checkpoint 推进结果可解释。

### 10.4 真实网页测试

使用本地专用 Profile 和指定频道验证：

- 至少 1000 条消息；
- 消息 ID、作者 ID、频道 ID、时间、正文；
- 回复关系；
- 引用目标或内容；
- 附件元数据和链接；
- 分页或虚拟滚动连续性；
- 二次运行不新增重复消息；
- 真实 OpenCLI 输出可转换为 Canonical Schema。
- bounded soak 和 1000 条运行均必须提供逐页阶段耗时、network 尝试次数、响应匹配状态和失败分类。
- 报告必须同时给出正常页面耗时分布和失败/重试耗时分布；不能只报告整个进程的总墙钟时间。

每项都要提供证据，不以“页面上看起来正常”作为通过依据。

### 10.5 故障注入测试

仅在 fixture 轨验证：

- 网络超时；
- 页面读取失败；
- 分页缺口；
- 进程中断；
- Schema 错误；
- 重复消息；
- 消息冲突；
- 缺失回复目标；
- 部分批次成功。

验证失败是否被准确分类，以及是否错误推进 checkpoint。

### 10.6 最终判定

报告必须分别给出：

- OpenCLI 真实网页能力；
- Canonical Schema 合约；
- 增量与恢复逻辑；
- 安全前置条件；
- 未验证项；
- 阻断问题；
- OpenCLI-first 的 Go/No-Go 建议。

任何硬性字段失败、真实网页采集无法达到 1000 条、明显漏采或错误归因，均不得给出整体通过结论。

## 11. Spike 交付物

Spike 完成后形成：

- OpenCLI 能力结论：通过、部分通过或不通过；
- 最小 Canonical Schema 草案；
- 原始字段到 Canonical Schema 的映射表；
- checkpoint 与增量行为报告；
- 失败场景和缺口清单；
- 是否继续 OpenCLI-first 的建议；
- 需要进入后续 V0/V1 Spec 的未决项。

真实采集结果和真实 fixture 只保存在本地，不进入仓库。

## 12. 后续决策边界

本 Spike 结束后，只有在书面证据审阅完成的前提下，才能决定：

- 是否继续 OpenCLI-first；
- 是否需要设计 OpenCLI 私有 Adapter；
- 是否需要单独开展 Discord Desktop OpenCLI adapter 的局部 Spike；
- 是否继续使用 Browser Bridge network 响应，或改用已验证的定向响应等待策略；
- 是否需要为真实网页轨增加独立的采集耗时预算和运行监控；
- Canonical Schema 是否进入 V0/V1 正式 Spec；
- checkpoint、Worker 和持久化模型如何正式设计；
- 是否单独开展局部 Playwright/CDP 后备方案 Spike。

本文件不批准任何生产实现，也不批准 V0、V1、V2 或 V3 的实施。

## 13. Spec 自检

- 范围检查：只包含 Spike-01，没有把 V0–V3 合并为实现任务。
- 非目标检查：已明确排除生产代码、应用框架、生产依赖、LLM、X 和后备采集器。
- 一致性检查：真实网页轨负责 OpenCLI 能力，fixture 轨负责确定性增量行为，两者在 Connector 后汇合。
- 失败检查：环境失败、harness 缺陷、OpenCLI 缺口和数据完整性失败已分开处理。
- 安全检查：真实账号、Cookie、Profile、私有数据和真实 fixture 均禁止进入 Git 或云端。
- 验收检查：硬性字段、1000 条真实采集、幂等、恢复、checkpoint 和失败隔离均有明确判定。
- Revision-01 检查：1000 条必须由采集器真实取得；bounded soak、逐页遥测、响应新鲜度和页面硬截止时间均有明确任务；人工导出不构成验收替代。
- 占位符检查：无 TODO、TBD 或未定义的模糊占位项。

自检结论：文档内部无已发现的范围冲突或未处理的占位项；后续未决事项属于 Spike 结果产生后的正式 Spec 决策，不是本文件的缺失。
