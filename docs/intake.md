# Invest Hub 模块 1：投资信息收集 — Intake

## 1. 文档目的

本文档用于向 Codex Superpowers 提供 Invest Hub 项目的需求输入，供后续继续完成：

1. 需求澄清与架构设计；
2. 技术 Spike；
3. 正式 Spec；
4. 分版本实施 Plans；
5. 测试与验收标准。

本文档不是实现方案，也不包含代码。部分技术细节仍需通过 Spike 或 Spec 阶段继续确认，本文已明确标注。

---

## 2. 项目背景

Invest Hub 是一个面向个人及少量受邀用户的投资信息与投资决策工作台，目标是持续沉淀外部投研信息、个人判断、交易策略和复盘结果，并最终帮助用户形成稳定的个人投资体系。

完整产品后续计划包括：

1. 模块 1：投资信息收集；
2. 模块 2：选股研判；
3. 模块 3：策略和复盘；
4. 模块 4：投资体系。

本阶段只开发和讨论模块 1，但模块 1 的数据结构应为后续模块保留可关联能力，例如来源、作者、标的、时间、观点、操作倾向、证据和摘要版本。

---

## 3. 本阶段产品目标

模块 1 的核心不是简单搬运 Discord 和 X 内容，而是建立一条可持续运行的个人投研信息加工流水线：

外部信息采集  
→ 原始内容持久化  
→ 规则清洗  
→ LLM 结构化理解  
→ 分批次总结  
→ 日累计总结  
→ 网页阅读与证据回溯

模块 1 首版需要支持：

1. 从用户已登录的 Discord 网页版私有频道中增量采集消息；
2. 从用户已登录的 X 网页版中采集指定博主内容；
3. 使用可切换 LLM Provider 进行分类、提炼和总结；
4. 通过网页查看自然日、批次、频道或博主维度的总结；
5. 支持管理员配置频道、指定用户、博主、邀请码、Prompt 和 LLM Provider；
6. 支持本地 Worker 自动更新、离线补采、错误重试和任务恢复；
7. 支持少量受邀用户共享阅读同一套数据。

## 4. 核心产品原则

### 4.1 事实优先

所有总结必须基于实际采集到的文本内容。未解析的图片、视频、语音和外部文章正文不得被 LLM 臆测。

LLM 输出必须能够区分：

- 原始事实；
- 发言者观点；
- 系统归纳；
- 不确定判断。

### 4.2 内容优先

网页阅读层以总结内容为主，运行状态、生成时间、消息覆盖范围和 Provider 等元信息后置。

### 4.3 可追溯

原始消息和帖子保留一年。摘要长期保留。在原始数据保留期内，用户可以从总结下钻到原始消息或原始链接。

### 4.4 增量处理

所有来源按 checkpoint 增量同步。电脑错过定时任务后，应在本地 Worker 恢复运行时继续补采，不依赖某个固定时间点必须在线。

### 4.5 低成本优先

V1 优先使用免费技术栈和免费 LLM API，但必须通过任务拆分、低并发、局部重试、结构化缓存和 Codex CLI fallback 保证最终可用性。

### 4.6 可迁移

V1 使用海外免费云服务，但后续可能迁移到中国大陆境内部署。认证、数据库、任务系统和 LLM Provider 不应过度绑定单一平台。

## 5. 用户与权限

### 5.1 用户角色

系统只需要两个角色。

#### 管理员

管理员可以：

- 查看全部内容；
- 管理 Discord 频道；
- 管理 Discord 指定用户；
- 管理 X 指定博主；
- 生成和停用邀请码；
- 手动触发 Discord 或 X 更新；
- 查看任务状态和简化错误；
- 手动重试失败任务；
- 编辑和启用 Prompt；
- 查看和切换 LLM Provider。

#### 普通用户

普通用户可以：

- 登录后查看全部已生成内容；
- 查看 Discord 总结；
- 查看 X 总结与原始链接；
- 展开原始消息和历史版本。

普通用户不能：

- 进入配置中心；
- 手动触发更新；
- 查看任务管理；
- 修改 Prompt；
- 修改 Provider；
- 管理邀请码或信息源。

### 5.2 数据空间

所有用户共享同一套 Discord、X 和总结数据。

V1 不支持：

- 用户独立信息源；
- 用户独立数据空间；
- 已读未读；
- 未读数量；
- 服务端阅读进度。

Next.js 同时承担：

- 邀请码校验；
- 管理员操作；

Supabase 承担：

- PostgreSQL；

- RLS；

- 摘要；

- 任务状态；
- Worker 心跳。

### 7.2 本地执行面

用户的 Mac 上运行 Invest Hub Worker。

Worker 形态：

- 命令行脚本或常驻进程；
- 使用 macOS `launchd` 开机启动和异常拉起；
- 提供安装、更新、状态查看和卸载命令；
- 不需要图形化桌面应用。

Worker 负责：

- 读取云端配置；
- 上报心跳；
- 拉取任务；
- 控制专用 Chrome Profile；
- 调用 OpenCLI；
- 采集 Discord；
- 采集 X；
- 规则清洗；
- 调用 LLM Provider；
- 生成批次总结；
- 生成或更新日累计总结；
- 局部重试；
- 状态上报；
- 日志记录。

### 7.3 Chrome Profile

V1 使用一个专用 Chrome Profile，同时登录：

- Discord；
- X。

专用 Profile 不登录邮箱、金融账户或其他无关账号。

后续若 Discord 和 X 出现登录冲突、风控差异或稳定性问题，可以拆成两个 Profile。

## 8. 信息采集架构

### 8.1 OpenCLI-first

Invest Hub 采用 OpenCLI-first 方案。

OpenCLI 作为：

- 浏览器采集 Runtime；
- 登录态复用层；
- Browser Bridge；
- DOM 与网络数据读取层；
- Adapter/Plugin 执行框架；
- 跨平台扩展基础设施。

Invest Hub 不应让业务逻辑直接依赖 OpenCLI 原始输出。

系统需要额外维护：

- DiscordConnector；
- XConnector；
- Invest Hub Canonical Schema；
- OpenCLI 输出到 Canonical Schema 的转换层。

Playwright/CDP 只作为 OpenCLI 无法满足特定场景时的局部后备实现，不提前建设完整第二套采集框架。

### 8.2 Canonical Schema

Discord 与 X 的数据需要统一转换到 Invest Hub 自己的数据结构。

建议至少包含：

- source_type；
- source_account_id；
- source_container_id；
- external_item_id；
- author_id；
- author_name；
- published_at；
- content_text；
- content_type；
- parent_item_id；
- quoted_item；
- attachments；
- source_url；
- raw_payload；
- collected_at。

具体字段和表结构由 Spec 阶段确认。

### 8.3 OpenCLI 版本管理

OpenCLI 不自动跟随最新版。

要求：

- 锁定具体版本；
- 升级前执行 Adapter Contract Test 和 authenticated smoke test；
- 升级失败可回滚；
- 不允许 OpenCLI 版本变化直接破坏生产采集。

## 9. Discord 功能需求

### 9.1 数据来源

Discord 数据源全部是：

- 用户本人已加入；
- 用户已付费或有权限访问；
- 用户在 Chrome 网页版 Discord 中正常可见的频道。

不采集未加入、无权限或无法正常访问的频道。

### 9.2 频道配置

配置中心支持管理员：

- 新增频道；
- 编辑频道；
- 启用频道；
- 停用频道；
- 填写频道名称；
- 填写 Discord 频道 URL；
- 查看验证状态；
- 查看最近成功采集时间；
- 配置频道级指定用户覆盖。

V1 新增方式：

管理员手动填写频道名称和 URL  
→ 云端保存为待验证  
→ Worker 使用 OpenCLI 验证访问权限  
→ 验证成功后启用  
→ 从验证成功时建立初始 checkpoint

V1 不自动读取账号全部可访问频道列表。

### 9.3 频道状态

建议至少包含：

- 待验证；
- 已启用；
- 访问失败；
- 已停用。

### 9.4 更新策略

所有 Discord 频道统一更新：

- 北京时间 08:00；
- 北京时间 20:50。

管理员可以单独手动触发 Discord 更新。

普通用户不能触发。

### 9.5 首次启用

首次启用频道：

- 不回溯历史；
- 从启用时刻建立初始 checkpoint；
- 只采集之后的新消息。

### 9.6 离线补采

电脑未在定时时间在线时：

- 不视为永久失败；
- Worker 恢复后读取每个频道 checkpoint；
- 从最后成功位置继续抓取；
- 一直追平到当前最新消息；
- 不能重复入库；
- 不能漏掉已产生的新消息；
- 某个频道失败不能阻断其他频道。

checkpoint 只有在数据成功持久化后才能推进。

### 9.7 指定用户

系统支持：

- 全局指定用户名单；
- 频道级新增；
- 频道级停用；
- 频道级排除；
- 频道级配置优先于全局配置。

指定用户内部必须使用 Discord 唯一用户 ID，不可只依赖昵称。

建议保存：

- Discord user ID；
- 当前显示名；
- 管理员备注名；
- 全局启用状态；
- 频道覆盖状态；
- 所属或适用频道。

### 9.8 消息处理范围

指定用户：

- 原则上所有文本消息都进入分析；
- 其回复、引用和必要上下文必须保留。

普通用户：

- 只保留投资相关内容；
- 或作为指定用户观点的必要上下文；
- 无关生活闲聊可以排除；
- 原始消息仍完整保存一年。

消息处理结果建议标记为：

- included；
- excluded；
- context_only；
- pending_review。

### 9.9 Discord 媒体

V1 不解析：

- 图片；
- 截图；
- PDF；
- 表格附件；
- 视频；
- 语音；
- 其他文件。

只保存：

- 文件名；
- 类型；
- 链接；
- 附件元数据。

如果核心信息依赖未解析附件，系统应标记“内容依赖附件，未解析”，不得生成确定性结论。

## 10. Discord LLM 总结需求

### 10.1 批次独立

每个运行批次独立完成：

- 规则清洗；
- 动态分块；
- 批次内话题识别；
- 局部结构化总结；
- 程序聚合；
- 必要时批次精炼。

V1 不维护跨批次长期 Topic Memory。

### 10.2 批次总结栏目

批次总结固定栏目顺序：

1. 重点人物观点；
2. 核心讨论；
3. 涉及标的；
4. 操作倾向；
5. 市场情绪；
6. 投资方法与心态；
7. 其他重要讨论。

没有内容的栏目不展示。

其中以下栏目只统计指定用户：

- 重点人物观点；
- 操作倾向；
- 投资方法与心态。

以下栏目统计全频道：

- 核心讨论；
- 涉及标的；
- 市场情绪；
- 其他重要讨论。

### 10.3 核心讨论数量

核心讨论：

- 最多展示 5 个话题；
- 按重要性排序；
- 数据层仍保存全部有效话题。

其他重要讨论：

- 不设固定条数上限；
- 每条必须高度压缩；
- 不得重复核心讨论。

### 10.4 批次摘要长度

采用软上限：

- 默认约 1500—2500 个中文字符；
- 高价值内容多时允许超过；
- 不硬截断；
- 优先压缩重复内容、背景铺垫和低重要性讨论；
- 不压缩指定用户明确操作、重大风险和观点变化。

### 10.5 证据展示

V1 页面采用栏目级证据入口：

- 每个栏目可展开查看其引用的原始消息；
- 原始消息按时间顺序展示；
- 暂不在每条具体观点后提供独立证据入口。

后台仍应保留观点或话题与原始消息 ID 的更细关联能力。

## 11. Discord 日累计总结

### 11.1 生成频率

每个频道在每个运行批次完成后，都需要生成或更新一次当天的日累计总结。

例如：

- 08:00 自动运行后，生成当天第一版日累计总结；
- 20:50 自动运行后，生成当天第二版日累计总结；
- 手动运行完成后，再生成新版本。

每次生成新版本时：

- 页面默认展示最新版；
- 历史版本默认折叠；
- 旧版本不可变。

### 11.2 输入范围

日累计总结不读取全天全部原始消息。

输入应为：

- 当前自然日已完成批次的结构化话题结果；
- 指定用户观点；
- 群聊主流观点；
- 操作倾向；
- 涉及标的；
- 情绪；
- 批次时间。

每次重新读取当天所有已成功批次的结构化结果，再生成完整最新版，而不是在旧日累计文本后直接续写。

### 11.3 日累计总结内容

日累计总结比批次总结更短，只突出：

1. 全天核心结论，最多 3—5 条；
2. 指定用户观点变化；
3. 群聊整体变化；
4. 重点风险与待跟踪事项。

指定用户变化和群聊整体变化必须明确区分。

如果只有一个批次，没有明确观点变化，对应栏目可以不展示。

### 11.4 异常规则

如果某个批次采集成功但批次总结失败：

- 日累计总结保持上一版本；
- 页面标记存在未完成批次；
- 待失败批次重试成功后再生成新版本。

## 12. X 功能需求

### 12.1 数据来源

X 使用专用 Chrome Profile 中已登录的 X 账号。

### 12.2 博主配置

配置中心支持：

- 新增博主；
- 编辑博主；
- 启用博主；
- 停用博主；
- 查看验证状态；
- 查看最近成功更新时间。

### 12.3 首次启用

首次启用博主：

- 不回溯历史；
- 从启用时刻建立 checkpoint；
- 只采集之后的新内容。

### 12.4 更新策略

X 更新频率与 Discord 一致：

- 北京时间 08:00；
- 北京时间 20:50；
- 管理员手动更新。

Discord 与 X 任务独立，互不阻塞。

### 12.5 内容类型

需要采集：

- 原创帖；
- 引用帖；
- 回复；
- 普通转发。

系统必须保留内容类型。

### 12.6 处理规则

原创帖：

- 总结博主自己的观点。

引用帖：

- 区分博主附加评论；
- 区分被引用内容；
- 总结博主对引用内容的态度。

回复：

- 保留被回复内容；
- 不得脱离上下文总结。

普通转发：

- 保留转发内容；
- 标注“无附加评论转发”；
- 不得直接表述为博主明确认同。

外部文章：

- 只读取 X 页面可见标题、摘要和卡片信息；
- 不打开正文；
- 信息不足时只保留链接；
- 明确标注“未读取正文”。

媒体：

- 图片不理解；
- 长图不 OCR；
- 视频不转写；
- 语音不转写；
- 只保留链接和媒体类型；
- 核心信息依赖媒体时标记“媒体内容未解析”。

### 12.7 X 摘要语言

无论原文语言为何：

- 摘要统一输出中文；
- 原文保留；
- ticker、公司名、ETF、缩写和专业词汇保留原文；
- 不确定翻译或语义需要明确标注。

### 12.8 X 摘要结构

每个博主每个运行批次独立总结。

固定栏目：

1. 核心观点；
2. 涉及标的；
3. 操作倾向；
4. 引用与转发内容；
5. 态度变化；
6. 其他重要内容。

没有内容的栏目不展示。

不做跨博主综合总结。

## 13. LLM 处理架构

### 13.1 Provider

V1 必须完整支持：

- GLM API；
- Codex CLI；
- Mock Provider。

配置中心可以：

- 查看当前 Provider；
- 查看健康状态；
- 查看最近健康检查时间；
- 切换全局默认 Provider。

### 13.2 默认运行策略

默认模式：

- GLM 处理任务；
- GLM 同一任务自动重试 3 次；
- 仍失败后自动 fallback 到 Codex CLI。

系统也允许管理员将 Codex CLI 设置为全局默认 Provider。

### 13.3 LLM 任务优化

为降低免费 API 调用次数和失败率，正式链路采用：

规则清洗  
→ 单次 chunk 结构化分析  
→ 程序聚合  
→ 必要时一次批次精炼  
→ 每次运行后生成或更新一次日累计总结

“语义分类、话题识别、局部总结”尽量在同一次 chunk 调用中完成。

### 13.4 确定性工作由程序完成

程序负责：

- 去重；
- 系统消息过滤；
- 纯表情过滤；
- 回复关系还原；
- 作者识别；
- 指定用户识别；
- ticker、价格、百分比和 URL 提取；
- 时间排序；
- Top 5 截取；
- 消息 ID 存在性校验；
- 指定用户身份校验；
- JSON Schema 校验；
- 重复话题初筛；
- 相同 ticker 候选合并；
- 输出字段缺省补齐。

### 13.5 动态分块

V1 使用动态分块，不固定按消息条数切分。

建议原则：

- 先按时间连续性形成候选块；
- 回复和引用关系尽量保留在同一块；
- 指定用户消息及必要上下文尽量同块；
- 达到 Provider 安全输入上限前停止；
- 相邻块保留少量重叠消息；
- 超长话题再二级切分；
- 后续子块可携带前一子块摘要。

以下参数在 Spike 后确定，不在 intake 中写死：

- 时间断点阈值；
- 最大安全输入 token；
- 最大输出 token；
- 重叠消息数量；
- 指定用户前后上下文数量；
- Provider 并发；
- Provider 请求间隔。

### 13.6 低并发

V1 默认：

- Provider 全局低并发；
- 可先设为 1；
- 不同频道串行或受控排队；
- Discord 和 X 不同时高并发调用；
- 允许任务处理时间较长；
- 网页展示实时状态。

### 13.7 任务恢复

每个 chunk 都需要稳定 ID，建议由以下信息确定：

- 来源；
- 频道或博主；
- 批次；
- 消息起止 ID；
- Prompt 版本；
- Provider；
- 处理类型。

保存：

- 输入范围；
- 状态；
- 重试次数；
- Provider；
- Prompt 版本；
- 原始响应；
- 结构化结果；
- Schema 校验结果；
- 错误类型。

单个 chunk 失败时：

- 只重试该 chunk；
- 已完成 chunk 不重复调用；
- 任务恢复后从未完成节点继续。

### 13.8 失败分类

网络超时或限流：

- 指数退避；
- 延迟重试；
- 不连续快速撞限流。

输出截断：

- 降低 chunk 大小；
- 或拆分子 chunk；
- 不原样重试。

JSON 错误：

- 先程序修复；
- 无法修复时可发起短格式修复请求；
- 不优先完整重跑。

内容遗漏：

- 只补充遗漏内容；
- 与已有结果合并；
- 不整块重跑。

Provider 不可用：

- 进入等待或 fallback；
- 不立即判定永久失败。

## 14. Prompt 管理

### 14.1 配置范围

Discord 所有频道共用一组 Prompt。

X 所有博主共用一组 Prompt。

不支持频道级或博主级 Prompt 覆盖。

### 14.2 Prompt 分层

系统固定层：

- 输出 JSON Schema；
- 字段定义；
- 证据规则；
- 不得臆测；
- 指定用户规则；
- 媒体未解析规则；
- 事实与推断区分。

管理员可编辑层：

- 关注重点；
- 过滤偏好；
- 总结风格；
- 栏目解释；
- 表达长度；
- 对特定投资内容的偏好。

管理员不能破坏系统固定层。

### 14.3 Prompt 工作流

Prompt 采用：

草稿  
→ fixture 测试  
→ 测试通过  
→ 启用

保存新 Prompt 后不立即生效。

### 14.4 Prompt 版本

每个 Prompt 版本至少记录：

- Prompt 类型；
- 版本号；
- 创建时间；
- 修改人；
- 是否当前版本；
- 变更说明；
- 测试结果。

摘要需要记录实际使用的 Prompt 版本。

V1 支持：

- 查看历史版本；
- 恢复旧版本；
- 不需要文本 diff。

## 25. 成功定义

模块 1 成功的标准不是“网页能够展示 Discord 和 X 内容”，而是：

- 能长期稳定采集；
- 电脑离线后能补采；
- 原始数据不丢失；
- 指定用户和博主观点不错误归因；
- 免费 LLM 失败时可以局部重试或 fallback；
- 高消息量下任务仍可最终完成；
- 日累计总结能突出核心点和观点变化；
- 用户可以从自然日和批次层级快速阅读；
- 用户需要时可以追溯到原始消息和原始链接；
- 系统具备明确测试门禁、日志、恢复和后续扩展能力。
