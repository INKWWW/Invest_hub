# Invest Hub 模块 1：投资信息收集 — Intake

## 1. 文档目的

本文档用于向 Codex Superpowers 提供 Invest Hub 项目的需求输入，供后续继续完成：

1. 需求澄清与架构设计；
2. 技术 Spike；
3. 正式 Spec；
4. 分版本实施 Plans；
5. 测试与验收标准。

本文档不是实现方案，也不包含代码。部分技术细节仍需通过 Spike 或 Spec 阶段继续确认，本文已明确标注。

### 当前 Provider 决策与历史说明

本文中涉及 **GLM API** 或 **GLM 失败后自动 fallback 到 Codex CLI** 的内容，均为早期方案记录，现阶段暂不考虑，也不构成后续实现授权。

当前路线为：**Codex CLI 是唯一真实 LLM Provider 候选；Mock Provider 仅用于确定性测试；不实现 GLM API 或自动 Provider fallback。** 若未来要重新引入 GLM、其他真实 Provider 或自动 fallback，必须先完成独立 Spike、Spec 和 implementation plan 的审阅与批准。

下文保留早期方案的原始讨论，以记录决策演变；与本说明冲突时，以上当前决策优先。

## 2. 项目背景

Invest Hub 是一个面向个人及少量受邀用户的投资信息与投资决策工作台，目标是持续沉淀外部投研信息、个人判断、交易策略和复盘结果，并最终帮助用户形成稳定的个人投资体系。

完整产品后续计划包括：

1. 模块 1：投资信息收集；
2. 模块 2：选股研判；
3. 模块 3：策略和复盘；
4. 模块 4：投资体系。

本阶段只开发和讨论模块 1，但模块 1 的数据结构应为后续模块保留可关联能力，例如来源、作者、标的、时间、观点、操作倾向、证据和摘要版本。

---

## 3. 本阶段产品目标

模块 1 的核心不是简单搬运 Discord 和 X 内容，而是建立一条可持续运行的个人投研信息加工流水线：

外部信息采集  
→ 原始内容持久化  
→ 规则清洗  
→ LLM 结构化理解  
→ 分批次总结  
→ 日累计总结  
→ 网页阅读与证据回溯

模块 1 首版需要支持：

1. 从用户已登录的 Discord 网页版私有频道中增量采集消息；
2. 从用户已登录的 X 网页版中采集指定博主内容；
3. 使用可切换 LLM Provider 进行分类、提炼和总结；
4. 通过网页查看自然日、批次、频道或博主维度的总结；
5. 支持管理员配置频道、指定用户、博主、邀请码、Prompt 和 LLM Provider；
6. 支持本地 Worker 自动更新、离线补采、错误重试和任务恢复；
7. 支持少量受邀用户共享阅读同一套数据。

## 4. 核心产品原则

### 4.1 事实优先

所有总结必须基于实际采集到的文本内容。未解析的图片、视频、语音和外部文章正文不得被 LLM 臆测。

LLM 输出必须能够区分：

- 原始事实；
- 发言者观点；
- 系统归纳；
- 不确定判断。

### 4.2 内容优先

网页阅读层以总结内容为主，运行状态、生成时间、消息覆盖范围和 Provider 等元信息后置。

### 4.3 可追溯

原始消息和帖子保留一年。摘要长期保留。在原始数据保留期内，用户可以从总结下钻到原始消息或原始链接。

### 4.4 增量处理

所有来源按 checkpoint 增量同步。电脑错过定时任务后，应在本地 Worker 恢复运行时继续补采，不依赖某个固定时间点必须在线。

### 4.5 低成本优先

早期方案曾设想使用免费 LLM API，并以 Codex CLI 自动 fallback 保证最终可用性；该 Provider 组合现阶段暂不考虑。当前以 Codex CLI 为唯一真实 Provider 候选，通过任务拆分、低并发、局部重试和结构化缓存保证可恢复性。

### 4.6 可迁移

V1 使用海外免费云服务，但后续可能迁移到中国大陆境内部署。认证、数据库、任务系统和 LLM Provider 不应过度绑定单一平台。

## 5. 用户与权限

### 5.1 用户角色

系统只需要两个角色。

#### 管理员

管理员可以：

- 查看全部内容；
- 管理 Discord 频道；
- 管理 Discord 指定用户；
- 管理 X 指定博主；
- 生成和停用邀请码；
- 手动触发 Discord 或 X 更新；
- 查看任务状态和简化错误；
- 手动重试失败任务；
- 编辑和启用 Prompt；
- 查看和切换 LLM Provider。

#### 普通用户

普通用户可以：

- 登录后查看全部已生成内容；
- 查看 Discord 总结；
- 查看 X 总结与原始链接；
- 展开原始消息和历史版本。

普通用户不能：

- 进入配置中心；
- 手动触发更新；
- 查看任务管理；
- 修改 Prompt；
- 修改 Provider；
- 管理邀请码或信息源。

### 5.2 数据空间

所有用户共享同一套 Discord、X 和总结数据。

V1 不支持：

- 用户独立信息源；
- 用户独立数据空间；
- 已读未读；
- 未读数量；
- 服务端阅读进度。

- 命令行脚本或常驻进程；

- 提供安装、更新、状态查看和卸载命令；

Worker 负责：

- 读取云端配置；

- 状态上报；

### 7.3 Chrome Profile

V1 使用一个专用 Chrome Profile，同时登录：

- Discord；

专用 Profile 不登录邮箱、金融账户或其他无关账号。

后续若 Discord 和 X 出现登录冲突、风控差异或稳定性问题，可以拆成两个 Profile。

## 8. 信息采集架构

### 8.1 OpenCLI-first

Invest Hub 采用 OpenCLI-first 方案。

OpenCLI 作为：

- 浏览器采集 Runtime；
- 登录态复用层；
- Browser Bridge；
- DOM 与网络数据读取层；
- Adapter/Plugin 执行框架；
- 跨平台扩展基础设施。

Invest Hub 不应让业务逻辑直接依赖 OpenCLI 原始输出。

系统需要额外维护：

- DiscordConnector；
- XConnector；
- Invest Hub Canonical Schema；
- OpenCLI 输出到 Canonical Schema 的转换层。

Playwright/CDP 只作为 OpenCLI 无法满足特定场景时的局部后备实现，不提前建设完整第二套采集框架。

### 8.2 Canonical Schema

Discord 与 X 的数据需要统一转换到 Invest Hub 自己的数据结构。

建议至少包含：

- source_type；
- source_account_id；
- source_container_id；
- external_item_id；
- author_id；
- author_name；
- published_at；
- content_text；
- content_type；
- parent_item_id；
- quoted_item；
- attachments；
- source_url；
- raw_payload；
- collected_at。

具体字段和表结构由 Spec 阶段确认。

### 8.3 OpenCLI 版本管理

OpenCLI 不自动跟随最新版。

要求：

- 锁定具体版本；
- 升级前执行 Adapter Contract Test 和 authenticated smoke test；
- 升级失败可回滚；
- 不允许 OpenCLI 版本变化直接破坏生产采集。

## 9. Discord 功能需求

### 9.1 数据来源

Discord 数据源全部是：

- 用户本人已加入；
- 用户已付费或有权限访问；
- 用户在 Chrome 网页版 Discord 中正常可见的频道。

不采集未加入、无权限或无法正常访问的频道。

### 9.2 频道配置

配置中心支持管理员：

- 新增频道；
- 编辑频道；
- 启用频道；
- 停用频道；
- 填写频道名称；
- 填写 Discord 频道 URL；
- 查看验证状态；
- 查看最近成功采集时间；
- 配置频道级指定用户覆盖。

V1 新增方式：

管理员手动填写频道名称和 URL  
→ 云端保存为待验证  
→ Worker 使用 OpenCLI 验证访问权限  
→ 验证成功后启用  
→ 从验证成功时建立初始 checkpoint

V1 不自动读取账号全部可访问频道列表。

### 9.3 频道状态

建议至少包含：

- 待验证；
- 已启用；
- 访问失败；
- 已停用。

### 9.4 更新策略

所有 Discord 频道统一更新：

- 北京时间 08:00；
- 北京时间 20:50。

管理员可以单独手动触发 Discord 更新。

普通用户不能触发。

### 9.5 首次启用

首次启用频道：

- 不回溯历史；
- 从启用时刻建立初始 checkpoint；
- 只采集之后的新消息。

### 9.6 离线补采

电脑未在定时时间在线时：

- 不视为永久失败；
- Worker 恢复后读取每个频道 checkpoint；
- 从最后成功位置继续抓取；
- 一直追平到当前最新消息；
- 不能重复入库；
- 不能漏掉已产生的新消息；
- 某个频道失败不能阻断其他频道。

checkpoint 只有在数据成功持久化后才能推进。

### 9.7 指定用户

系统支持：

- 全局指定用户名单；
- 频道级新增；
- 频道级停用；
- 频道级排除；
- 频道级配置优先于全局配置。

指定用户内部必须使用 Discord 唯一用户 ID，不可只依赖昵称。

建议保存：

- Discord user ID；
- 当前显示名；
- 管理员备注名；
- 全局启用状态；
- 频道覆盖状态；
- 所属或适用频道。

### 9.8 消息处理范围

指定用户：

- 原则上所有文本消息都进入分析；
- 其回复、引用和必要上下文必须保留。

普通用户：

- 只保留投资相关内容；
- 或作为指定用户观点的必要上下文；
- 无关生活闲聊可以排除；
- 原始消息仍完整保存一年。

消息处理结果建议标记为：

- included；
- excluded；
- context_only；
- pending_review。

### 9.9 Discord 媒体

V1 不解析：

- 图片；
- 截图；
- PDF；
- 表格附件；
- 视频；
- 语音；
- 其他文件。

只保存：

- 文件名；
- 类型；
- 链接；
- 附件元数据。

如果核心信息依赖未解析附件，系统应标记“内容依赖附件，未解析”，不得生成确定性结论。

## 10. Discord LLM 总结需求

### 10.1 批次独立

每个运行批次独立完成：

- 规则清洗；
- 动态分块；
- 批次内话题识别；
- 局部结构化总结；
- 程序聚合；
- 必要时批次精炼。

V1 不维护跨批次长期 Topic Memory。

### 10.2 批次总结栏目

批次总结固定栏目顺序：

1. 重点人物观点；
2. 核心讨论；
3. 涉及标的；
4. 操作倾向；
5. 市场情绪；
6. 投资方法与心态；
7. 其他重要讨论。

没有内容的栏目不展示。

其中以下栏目只统计指定用户：

- 重点人物观点；
- 操作倾向；
- 投资方法与心态。

以下栏目统计全频道：

- 核心讨论；
- 涉及标的；
- 市场情绪；
- 其他重要讨论。

### 10.3 核心讨论数量

核心讨论：

- 最多展示 5 个话题；
- 按重要性排序；
- 数据层仍保存全部有效话题。

其他重要讨论：

- 不设固定条数上限；
- 每条必须高度压缩；
- 不得重复核心讨论。

### 10.4 批次摘要长度

采用软上限：

- 默认约 1500—2500 个中文字符；
- 高价值内容多时允许超过；
- 不硬截断；
- 优先压缩重复内容、背景铺垫和低重要性讨论；
- 不压缩指定用户明确操作、重大风险和观点变化。

### 10.5 证据展示

V1 页面采用栏目级证据入口：

- 每个栏目可展开查看其引用的原始消息；
- 原始消息按时间顺序展示；
- 暂不在每条具体观点后提供独立证据入口。

后台仍应保留观点或话题与原始消息 ID 的更细关联能力。

## 11. Discord 日累计总结

### 11.1 生成频率

每个频道在每个运行批次完成后，都需要生成或更新一次当天的日累计总结。

例如：

- 08:00 自动运行后，生成当天第一版日累计总结；
- 20:50 自动运行后，生成当天第二版日累计总结；
- 手动运行完成后，再生成新版本。

每次生成新版本时：

- 页面默认展示最新版；
- 历史版本默认折叠；
- 旧版本不可变。

### 11.2 输入范围

日累计总结不读取全天全部原始消息。

输入应为：

- 当前自然日已完成批次的结构化话题结果；
- 指定用户观点；
- 群聊主流观点；
- 操作倾向；
- 涉及标的；
- 情绪；
- 批次时间。

每次重新读取当天所有已成功批次的结构化结果，再生成完整最新版，而不是在旧日累计文本后直接续写。

### 11.3 日累计总结内容

日累计总结比批次总结更短，只突出：

1. 全天核心结论，最多 3—5 条；
2. 指定用户观点变化；
3. 群聊整体变化；
4. 重点风险与待跟踪事项。

指定用户变化和群聊整体变化必须明确区分。

如果只有一个批次，没有明确观点变化，对应栏目可以不展示。

### 11.4 异常规则

如果某个批次采集成功但批次总结失败：

- 日累计总结保持上一版本；
- 页面标记存在未完成批次；
- 待失败批次重试成功后再生成新版本。

## 12. X 功能需求

### 12.1 数据来源

X 使用专用 Chrome Profile 中已登录的 X 账号。

### 12.2 博主配置

配置中心支持：

- 新增博主；
- 编辑博主；
- 启用博主；
- 停用博主；
- 查看验证状态；
- 查看最近成功更新时间。

### 12.3 首次启用

首次启用博主：

- 不回溯历史；
- 从启用时刻建立 checkpoint；
- 只采集之后的新内容。

### 12.4 更新策略

X 更新频率与 Discord 一致：

- 北京时间 08:00；
- 北京时间 20:50；
- 管理员手动更新。

Discord 与 X 任务独立，互不阻塞。

### 12.5 内容类型

需要采集：

- 原创帖；
- 引用帖；
- 回复；
- 普通转发。

系统必须保留内容类型。

### 12.6 处理规则

原创帖：

- 总结博主自己的观点。

引用帖：

- 区分博主附加评论；
- 区分被引用内容；
- 总结博主对引用内容的态度。

回复：

- 保留被回复内容；
- 不得脱离上下文总结。

普通转发：

- 保留转发内容；
- 标注“无附加评论转发”；
- 不得直接表述为博主明确认同。

外部文章：

- 只读取 X 页面可见标题、摘要和卡片信息；
- 不打开正文；
- 信息不足时只保留链接；
- 明确标注“未读取正文”。

媒体：

- 图片不理解；
- 长图不 OCR；
- 视频不转写；
- 语音不转写；
- 只保留链接和媒体类型；
- 核心信息依赖媒体时标记“媒体内容未解析”。

### 12.7 X 摘要语言

无论原文语言为何：

- 摘要统一输出中文；
- 原文保留；
- ticker、公司名、ETF、缩写和专业词汇保留原文；
- 不确定翻译或语义需要明确标注。

### 12.8 X 摘要结构

每个博主每个运行批次独立总结。

固定栏目：

1. 核心观点；
2. 涉及标的；
3. 操作倾向；
4. 引用与转发内容；
5. 态度变化；
6. 其他重要内容。

没有内容的栏目不展示。

不做跨博主综合总结。

## 13. LLM 处理架构

> **历史说明：** 本节中关于 GLM API、GLM 默认处理和自动 fallback 的细节属于早期方案，现阶段暂不考虑。当前只采用 Codex CLI 作为真实 Provider 候选，Mock Provider 仅用于确定性测试；失败保留分类状态并局部重试，不自动切换 Provider。

### 13.1 Provider

V1 必须完整支持：

- GLM API；
- Codex CLI；
- Mock Provider。

配置中心可以：

- 查看当前 Provider；
- 查看健康状态；
- 查看最近健康检查时间；
- 切换全局默认 Provider。

### 13.2 早期默认运行策略（暂不考虑）

默认模式：

- GLM 处理任务；
- GLM 同一任务自动重试 3 次；
- 仍失败后自动 fallback 到 Codex CLI。

系统也允许管理员将 Codex CLI 设置为全局默认 Provider。

### 13.3 LLM 任务优化

为降低免费 API 调用次数和失败率，正式链路采用：

规则清洗  
→ 单次 chunk 结构化分析  
→ 程序聚合  
→ 必要时一次批次精炼  
→ 每次运行后生成或更新一次日累计总结

“语义分类、话题识别、局部总结”尽量在同一次 chunk 调用中完成。

### 13.4 确定性工作由程序完成

程序负责：

- 去重；
- 系统消息过滤；
- 纯表情过滤；
- 回复关系还原；
- 作者识别；
- 指定用户识别；
- ticker、价格、百分比和 URL 提取；
- 时间排序；
- Top 5 截取；
- 消息 ID 存在性校验；
- 指定用户身份校验；
- JSON Schema 校验；
- 重复话题初筛；
- 相同 ticker 候选合并；
- 输出字段缺省补齐。

### 13.5 动态分块

V1 使用动态分块，不固定按消息条数切分。

建议原则：

- 先按时间连续性形成候选块；
- 回复和引用关系尽量保留在同一块；
- 指定用户消息及必要上下文尽量同块；
- 达到 Provider 安全输入上限前停止；
- 相邻块保留少量重叠消息；
- 超长话题再二级切分；
- 后续子块可携带前一子块摘要。

以下参数在 Spike 后确定，不在 intake 中写死：

- 时间断点阈值；
- 最大安全输入 token；
- 最大输出 token；
- 重叠消息数量；
- 指定用户前后上下文数量；
- Provider 并发；
- Provider 请求间隔。

### 13.6 低并发

V1 默认：

- Provider 全局低并发；
- 可先设为 1；
- 不同频道串行或受控排队；
- Discord 和 X 不同时高并发调用；
- 允许任务处理时间较长；
- 网页展示实时状态。

### 13.7 任务恢复

每个 chunk 都需要稳定 ID，建议由以下信息确定：

- 来源；
- 频道或博主；
- 批次；
- 消息起止 ID；
- Prompt 版本；
- Provider；
- 处理类型。

保存：

- 输入范围；
- 状态；
- 重试次数；
- Provider；
- Prompt 版本；
- 原始响应；
- 结构化结果；
- Schema 校验结果；
- 错误类型。

单个 chunk 失败时：

- 只重试该 chunk；
- 已完成 chunk 不重复调用；
- 任务恢复后从未完成节点继续。

### 13.8 失败分类

网络超时或限流：

- 指数退避；
- 延迟重试；
- 不连续快速撞限流。

输出截断：

- 降低 chunk 大小；
- 或拆分子 chunk；
- 不原样重试。

JSON 错误：

- 先程序修复；
- 无法修复时可发起短格式修复请求；
- 不优先完整重跑。

内容遗漏：

- 只补充遗漏内容；
- 与已有结果合并；
- 不整块重跑。

Provider 不可用：

- 进入等待或可恢复失败，等待局部重试或人工处理；不自动 fallback；
- 不立即判定永久失败。

## 14. Prompt 管理

### 14.1 配置范围

Discord 所有频道共用一组 Prompt。

X 所有博主共用一组 Prompt。

不支持频道级或博主级 Prompt 覆盖。

### 14.2 Prompt 分层

系统固定层：

- 输出 JSON Schema；
- 字段定义；
- 证据规则；
- 不得臆测；
- 指定用户规则；
- 媒体未解析规则；
- 事实与推断区分。

管理员可编辑层：

- 关注重点；
- 过滤偏好；
- 总结风格；
- 栏目解释；
- 表达长度；
- 对特定投资内容的偏好。

管理员不能破坏系统固定层。

### 14.3 Prompt 工作流

Prompt 采用：

草稿  
→ fixture 测试  
→ 测试通过  
→ 启用

保存新 Prompt 后不立即生效。

### 14.4 Prompt 版本

每个 Prompt 版本至少记录：

- Prompt 类型；
- 版本号；
- 创建时间；
- 修改人；
- 是否当前版本；
- 变更说明；
- 测试结果。

摘要需要记录实际使用的 Prompt 版本。

V1 支持：

- 查看历史版本；
- 恢复旧版本；
- 不需要文本 diff。

### 15.3 Discord 页面

桌面端：

- 左侧固定频道列表；
- 主内容区展示日期和总结。

手机端：

- 顶部频道下拉；
- 单列卡片阅读。

切换频道时：

- 优先展示当前自然日；
- 当前日有部分数据时仍展示当前日；

展示结构：

自然日日期  
→ 日累计总结  
→ 当天各运行批次

日累计总结默认全部展开。

批次总结默认全部展开。

原始消息和历史版本默认折叠。

### 15.4 Discord 批次卡片

批次内容栏目顺序：

1. 重点人物观点；
2. 核心讨论；
3. 涉及标的；
4. 操作倾向；
5. 市场情绪；
6. 投资方法与心态；
7. 其他重要讨论。

卡片视觉顺序：

1. 完整总结内容；
2. 总结生成时间；
3. 实际覆盖消息时间范围；
4. 触发方式，自动或手动；
5. 当前状态。

正常成功状态放底部。

处理中、部分失败或失败状态需要提升到标题附近。

### 15.5 X 页面

X 页面按自然日展示：

自然日日期  
→ 博主  
→ 摘要  
→ 原始链接

每个博主默认完整展开。

每个博主展示：

- 当天最新版摘要；
- 对应原始 X 链接；
- 原帖发布时间；
- 原帖类型；
- 媒体类型或未解析标记。

同一天多次运行：

- 页面展示最新版；
- 历史版本折叠；
- 不做统一跨博主时间线。

### 15.6 视觉风格

整体风格：

- 简约；
- 信息清晰；
- 阅读优先；
- 微黄纸张底色；
- 护眼；
- 字体大小适中；
- 不使用花式字体；
- 不做投资数据大屏式三栏布局；
- 桌面和手机都可读。

### 15.7 移动端

V1 手机端主要保证阅读。

需要支持：

- Discord 日期与频道切换；
- 日累计总结；
- 批次总结；
- 原始消息展开；
- X 日期与博主内容；
- 原始链接；

## 26. V2 X 信息收集与阅读讨论补充（2026-07-22，待 Spec 确认）

本节记录 V2 Spec 起草前已讨论的产品输入，不构成 V2 技术选型、实现授权或验收结论。V2 必须独立完成 Spec 与 implementation plan 的审阅和批准后，才能开始实现。

### 26.1 采集对象与边界

- 采集对象是管理员配置的**指定 X 博主发布的消息**；“用户已登录且网页中正常可见”是访问与权限边界，不是筛选条件；
- 每位博主独立配置、checkpoint、任务、失败状态、重试与离线补采；单一博主的登录、页面或处理失败不得阻断其他博主；
- 必须区分原创、引用、回复和普通转发；引用中的博主评论与被引用原帖、回复与被回复上下文、无附加评论的普通转发不得混淆或错误归因为博主观点；
- 原帖标识、作者、发布时间、帖子类型、原始链接及附件/外链元数据应可追溯；图片、视频、PDF 与外部文章正文不解析、不臆测，只显示未解析边界或链接卡片；
- 当前真实 Provider 候选仍只有 Codex CLI，Mock Provider 仅用于确定性测试；GLM 与自动 fallback 仍是早期方案，暂不考虑。

### 26.2 阅读产品目标

用户进入 X 页面时，核心问题是“指定博主今天表达了什么、是否有观点或态度变化、原帖在哪里”，而不是浏览一个混合的 X 信息流。

- 每位博主、每个自然日生成独立的中文最新摘要，明确核心观点、涉及标的/主题、操作倾向或态度变化、不确定性及未解析内容提示；
- 同日多次同步时，前台显示最新版，历史版本默认折叠；
- 阅读页按“自然日 → 博主 → 最新摘要 → 原帖入口 → 历史版本”组织；不做跨博主统一结论、统一时间线或跨博主综合总结；
- 原帖入口默认折叠，只展示帖子类型、发布时间和“在 X 中打开”链接；管理员运行诊断、Worker、Prompt、凭据和本地引用不得进入普通阅读页；
- 页面必须区分处理中、部分失败、可重试失败、失败、无新增和成功，不能把失败显示为无内容。

### 26.3 页面信息架构输入

桌面端使用“博主范围选择 + 日期内容区”的阅读布局：左侧或顶部选择博主范围，主区先选自然日，再按博主卡片阅读。手机端使用顶部日期与博主选择器，单列展示博主卡片。

```text
X 日度研判
├── 日期与博主范围选择
├── 所选自然日
│   ├── 博主 A
│   │   ├── 当天最新版中文摘要（默认展开）
│   │   ├── 原帖入口：类型、时间、原始链接（默认折叠）
│   │   ├── 未解析媒体/外链提示
│   │   └── 历史版本（默认折叠）
│   ├── 博主 B
│   └── 其他已启用博主
└── 状态说明：处理中、部分失败、可重试失败、失败、无新增或成功

管理员专属
├── 指定博主配置、启停与授权状态
├── 手动更新与有界历史补采
└── 任务状态、失败分类与局部重试
```

### 26.4 V2 Spec 必须回答的未决问题

1. X 网页在已授权浏览器会话中的稳定采集方式、分页/无限滚动边界及真实验收样本；
2. 原创、引用、回复和普通转发的最小 Canonical 字段、去重身份和上下文关系；
3. 共享 `sources`、任务协议、Worker 能力与阅读导航如何从当前 Discord 专用边界安全扩展到 X；
4. 每博主每日摘要的精确栏目、Prompt 版本与事实/观点/不确定性校验；
5. 桌面与手机端的可读性、无障碍和状态展示验收标准；
6. 真实采集、存储、日志和原始链接在安全边界内的验收方式。

### 26.5 后续门禁

新 V2 会话先以本节、当前项目状态、V1/V1.1 工程日志为输入起草 V2 Spec；Spec 获批准后再编写 V2 implementation plan。任何 V2 代码、数据库迁移、共享协议改动、部署或真实 X 采集都不由本节授权。

## 27. 投资研究 Agent 独立能力模块输入（2026-08-11）

本节记录独立于既有模块 2–4 编号体系的投资研究 Agent 产品输入，不构成 Feature Contract、Delivery Plan 或实现授权。该独立能力仍须按照 Matt Pocock profile 完成完整 Spec 与 ticket graph 的审阅批准。

- **研究会话主题切换 TODO：** 评估让一个研究会话保持连贯研究目标、并在用户切换到实质无关的投资主题时创建新会话的实现与交互成本；如果首版成本过高，则不在首版实现，留待后续迭代。
- **Memory 首版边界：** 同一研究会话使用可压缩但可追溯的 Thread Memory；跨会话 Personal Long-term Memory 只包含 Interest Memory、Research Conclusion Memory 与 Preference Memory，不把完整聊天副本或系统 Skills 当作个人长期记忆。
- **Memory 写入与生命周期：** 已成功完成的 Agent Run 可以自动产生 Memory Candidate；低敏感关注信息和具备时间、条件、Run/Artifact 来源的关键结论可自动写入，真实持仓、资产规模和个人财务状况只能在用户明确要求后保存。历史结论不得被静默覆盖，应保留被取代或失效关系；用户可以查看、修改和删除自己的 Memory。
- **Thread Memory 压缩：** 完整聊天记录继续用于阅读和审计；进入模型上下文的内容可以压缩为最近对话、滚动摘要、当前研究状态与必要证据引用，且摘要必须能追溯到原始会话。
- **Agent Trace 与管理员审计：** 每次 Agent Run 必须形成结构化 Trace，覆盖编排步骤、模型与 Tool 调用元数据、耗时、用量、错误、输入输出摘要和 Artifact 引用；不得记录密钥、Cookie、浏览器凭据或模型隐藏思维过程，X/Discord 原始内容优先保留引用与 hash 而非在 Trace 中重复复制。管理员可以查看全部用户会话、Memory 与 Trace，管理员的查看、修改和删除操作本身必须留有审计记录。
- **可见研究过程：** 前端在 Agent Run 执行期间展示由真实 Runtime 事件、Tool 调用、来源进度、阶段性 Commentary 与 Provider 可提供的 Reasoning Summary 组成的用户安全过程；不展示原始 Chain-of-thought。运行时默认展开，完成后可以折叠并重新查看，失败时保留已完成步骤和安全失败原因。当前 Codex CLI Provider 尚未读取 JSONL 事件，首版必须先通过独立 Spike 确认 `codex exec --json` 的实际事件合同与脱敏边界，且前端合同不得绑定单一 Provider 的私有事件格式。
- **Codex CLI 帮助级事实：** 2026-08-11 本机 `codex-cli 0.144.3` 的帮助文本暴露 `codex exec --json`、`codex exec resume` 与 `--image`；这只证明命令入口存在，不证明 JSONL 事件 Schema 稳定、网站断线后可恢复、进程取消安全、Provider session 可作为 Research Thread 权威，或图片链路已满足项目隔离与保留要求。上述行为仍须在 Feature Contract 后通过代表性 Spike 验证。
- **Agent Skill 编排与准入：** Skill Description 用于发现候选、主动推荐与 Auto 路由；Agent 根据用户问题和研究上下文进行语义选择，Runtime 再确定性检查启用状态、固定版本、输入合同、Tool 权限、适用市场、调用上限和停止条件。外部 Skill 必须固定来源版本，经过许可证与安全审阅、必要的项目配置、Eval 和管理员试用后才能对普通用户启用；安装不等于启用。
- **Skill 提供约定：** 用户后续提供或安装的 Skill 默认只供 Codex 开发环境使用，不自动写入 Invest Hub 或成为网站 Runtime Skill；只有用户明确说明某个 Skill 专用于 Invest Hub 时，才进入项目的 Feature Contract、版本化适配与发布流程。本节列出的首批四个 Skill 已被用户明确指定用于 Invest Hub 网站 Agent，并允许进入后续导入流程。第三方 Skill 保留固定版本的上游原文，Invest Hub 只维护轻量的项目 Description、UI 文案与 Runtime 配置，不为本批次额外包装或重写其工作流。
- **Invest Hub Agent Skill 范围：** 核心 Agent 首批接入 `investment-research`、`investment-checklist` 与 `portfolio-review`。`investment-research` 用于用户明确要求对一家上市公司进行商业模式、护城河、管理层、行业、风险和估值的综合深度研究；`investment-checklist` 不依赖用户预先提供结构化投资逻辑，当用户明确提到正在作出投资决策或准备下单时，Agent 主动询问是否需要使用巴菲特买入前 Checklist，并在用户确认后使用，重点复核核心假设、反面证据、估值与安全边际、风险和决策纪律，不用于初次筛选或完整公司研究；`portfolio-review` 只在用户主动提供持仓并要求从组合层面分析集中度、相关性、风险、机会成本或调整方向时使用，不能仅因用户提到持有某只股票而自动调用。用户自研技术画线 Skill 与核心 Agent 并行开发，但不进入核心 Agent 的首个 Feature Contract；交付后通过独立集成 feature 接入。该 Skill 首版唯一有效输入是用户主动上传的 K 线截图，不支持只提供股票名称或代码后由系统取数，不接入富途，不获取 OHLCV，不生成原始 K 线图，也不预设其内部画线流程与输出边界。
- **显式 Skill 交互：** 聊天框上方展示可用 Skill 按钮；一次 Agent Run 最多允许用户点选一个，选中后在聊天输入区以可见引用呈现，并作为结构化选择随该次提问提交。未选择时进入 Auto，Agent 可以选择一个 Skill，也可以进行不依赖这些 Skill 的通用投资问答；用户显式选择后锁定该 Skill，不得静默切换为其他 Skill。若显式选择与输入不匹配，Agent 先说明缺失信息并追问，只有输入满足合同、Agent Run 正式开始后才扣 Research Quota。实际执行记录应显示最终使用的 Skill，选择不跨 Agent Run 永久保留。
- **Checklist 推荐交互：** Auto 识别到明确的投资决策或下单意图时，先询问用户是否使用“下单前巴菲特拷问”；用户以自然语言确认即可视为下一次 Agent Run 显式选择该 Skill，不要求再次点击按钮，并在输入区与实际执行记录中显示 Skill 引用。用户拒绝后，同一标的、同一次下单意图内不重复推荐；只有出现新的标的、新的下单决策或显著变化的投资条件时才可再次询问。
- **首批 Skill 按钮文案：** Auto 路由模式对用户显示为“智能”，`investment-research` 显示为“大师投研”，`investment-checklist` 显示为“下单前巴菲特拷问”，`portfolio-review` 显示为“持仓组合分析”，自研 Skill 暂用“技术画线分析”。展示文案与内部稳定 Skill ID、Auto 枚举分离，后续修改文案不得改变运行合同。
- **Agent 页面初步结构与原型结论：** 页面保持简洁的双栏聊天工作台：左侧显示当前用户自己的 Research Thread 列表，右侧显示当前 Thread 的多轮对话与对话框；可用 Skill 以轻量按钮放在对话框上方。整体视觉沿用当前 Invest Hub 的颜色、字体、边框、间距与交互语气，不另建一套通用 ChatGPT/Codex 仿制风格。2026-08-11 的 throwaway UI prototype 已选择 A“纸面工作台”作为后续 Feature Contract 的页面结构参考，B“Codex 专注界面”和 C“研究台”仅保留为被否决的比较材料。移动端结构、会话列表信息密度、对话消息层级、Research Progress 的展开方式和输入区控件继续在页面交互 Discovery 中确认。
- **X/Discord Agent sourcing 延期：** 首版投资研究 Agent 不设计、不开发、也不调用 Invest Hub 已有的 X 原始内容或 Discord 派生总结能力，不建设对应 Agent Tool、检索编排、引用合同或 Eval。现有 X/Discord 采集、持久化与 Reader 能力保持不变；未来若接入 Agent，必须作为独立能力重新完成 Feature Contract 与 Delivery Plan，本节不预留实现承诺。
- **首版事实来源：** Agent 可以使用用户提供的文字、上市公司或监管机构披露、公开网络资料，以及经过批准的行情与财务数据 Tool；不调用 X/Discord，也不允许任意 shell 或未经批准的数据源。具有时效性的外部事实必须显示来源与日期，来源不足时不得把模型已有知识伪装成当前事实。
- **自研技术画线 Skill 并行与集成门禁：** 核心 Agent Feature Contract 在用户明确批准时冻结，创建 draft `spec.md` 不构成冻结。自研 Skill 可以与核心 Agent 实现并行开发；核心只预留通用的版本化 Skill 准入边界，不提前实现推测性的图片上传或画线逻辑。Skill 交付后，单独完成“技术画线 Skill 集成”Feature Contract、ticket graph、输入输出与安全检查，再接入 Agent；集成发布前隐藏“技术画线分析”按钮。届时用户未上传 K 线截图只提示补充输入，不启动 Agent Run、不预占 Research Quota。
- **额度与并发：** 首版 Research Quota 是管理员手工分配的用户余额，不设计月度周期。Agent Run 正式开始时原子预占一次，成功形成研究回答后结算；Scope Refusal、补充信息追问、用户取消和技术失败均释放预占。单一用户同时最多运行一个 Agent Run。
- **Run 生命周期：** Agent Run 属于服务器侧可恢复任务，不依赖浏览器连接；刷新或重新打开页面后可以继续查看进度。用户可以停止正在运行的 Run，停止必须终止 Provider 进程并释放额度。首版不做回答分支、编辑后重跑或一键 Regenerate；失败后由用户明确发起新的重试 Run。
- **产品帮助例外：** Agent 可以回答 Invest Hub 自身功能、额度、会话和操作方式，并可以进行简短问候；该路径不调用研究 Tool、不写长期 Memory、不扣 Research Quota。其他非投资话题继续返回 Scope Refusal。
- **删除与保留：** 删除 Research Thread 时删除该用户可见的消息、Agent Run 与会话 Artifact，但不静默删除已独立形成的 Personal Long-term Memory；界面应提示用户到 Memory 管理页单独处理。只含脱敏运行元数据、不含聊天正文副本的 Trace 最长保留 30 天用于排错，之后自动清除。
- **用户与管理员管理面：** 用户账户菜单提供极简“我的记忆”页面，用于查看、修改和删除自己的 Memory；管理员现有 `/admin` 增加独立 Agent 管理工作区，用于管理用户额度并查看全部用户的 Research Thread、Memory 与 Trace。聊天左栏不承载管理功能。
- **A 原型交互确认：** Agent 作为独立顶层入口；Research Thread 自动生成短标题并允许用户重命名或删除，按时间分组；移动端左栏折叠为抽屉；页面持续显示剩余 Research Quota。首版不增加会话搜索、文件夹、收藏或分支。
- **Research Thread 权威：** Invest Hub 数据库是会话消息、Thread Memory、Personal Long-term Memory、Run 与 Artifact 的唯一事实来源。Codex Provider session 只能作为可丢弃的运行优化，不能成为多轮连续性的权威；任一 Run 必须能够从用户隔离的持久化上下文重建。
- **首版文件输入：** 核心 Agent 只接受文字输入，不支持 PDF、Word、Excel、CSV、财报截图或其他通用文件解析，也不为尚未交付的技术画线 Skill 提前建设上传入口。后续独立集成 feature 才按该 Skill 的实际合同增加 K 线截图上传；K 线截图是该 Skill 的强制输入，该能力不得被泛化为通用图片或文件上传。具体图片格式、大小、保留与删除规则由集成 Feature Contract 冻结。
- **本地 Worker 可用性：** 测试期明确接受网站 Agent 依赖用户本机 Codex CLI Worker 在线；电脑休眠、Worker 关闭或登录失效时，页面显示“Agent 暂时不可用”，历史 Research Thread 仍可读取，但不接受或无限排队新的 Agent Run，也不建设云端 Provider fallback。
- **首版资产范围：** 支持 A 股、港股、美股、ETF、基金和上市 REITs，以及直接服务于这些证券研究的行业、宏观、商品、估值、技术分析、投资方法、组合与风险问题。加密货币、外汇、衍生品交易、债券和非上市资产属于“暂不支持的投资范围”，不得误判为完全无关话题；纯暂不支持请求不启动 Agent Run、不扣 Research Quota。
- **混合话题：** 同一请求同时包含投资内容与无关内容时，只处理投资部分并明确拒绝其余部分；只要投资 Agent Run 正式执行，就正常结算一次额度。无关部分不进入研究 Tool、Trace 输入输出摘要或 Personal Long-term Memory。
- **管理员禁止冒充：** 管理员可以按已授权边界查看、修改或删除用户研究数据并管理额度，但不得以用户身份创建消息、继续 Research Thread 或发起 Agent Run。所有管理员操作必须保留真实管理员身份与审计记录。
- **证据不足与额度：** 公开来源不可用或互相矛盾时，Agent 只能输出已确认事实、分歧和缺失信息，不得生成确定性当前结论。若技术失败导致没有形成可用研究回答，则释放 Quota Reservation；若形成了可用的 Evidence-limited Result，则作为成功研究回答结算一次 Research Quota。
