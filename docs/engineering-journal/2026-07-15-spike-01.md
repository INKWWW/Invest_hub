# Spike-01 Engineering Journal

## 文档边界

本文档记录 Spike-01 执行期间实际发生的事件、尝试、失败和调整原因。它不是正式需求，也不是架构决策的唯一来源；正式范围以 Spec 为准，阶段结论以 Final Report 为准。

真实 Discord evidence 保存在本地受保护目录，不进入 Git。本文只记录脱敏计数、状态和技术现象，不记录真实消息正文、私有 URL、Profile 路径、Cookie 或 Token。

## 2026-07-15：开始执行

- 基于已批准的 Spike-01 Spec 和 Plan，在独立 worktree 中执行。
- 保持 Discovery 门禁：只创建 Spike harness、测试和证据记录，不初始化生产应用框架，不安装生产依赖。
- OpenCLI 版本为 1.8.6，daemon 和 Browser Bridge extension 连接正常。

## 2026-07-15：确定性轨先行

- 先完成 Canonical Schema、Validator、Local Evidence Store、Checkpoint Emulator 和 Fake Connector。
- 通过失败测试验证 checkpoint 后置推进、失败恢复、重复消息、未知关系和多来源隔离。
- 最终确定性测试为 32/32 通过。

## 2026-07-15：真实网页轨初次问题

- 首次 bounded soak 能够采集真实消息，但分页过程中出现 network entry 缺失。
- 页面仍可能有消息 DOM 节点，但没有可证明属于当前 cursor 的新 network response，因此不能直接接受 DOM 内容。
- 一次运行还暴露出当前浏览器 URL 可能是消息深链；直接拼接下一 cursor 会生成错误的嵌套路由。
- 另一次运行发现 Discord 登录态失效，页面跳转到登录页；该情况属于环境前置条件失败，不应判定为 OpenCLI 采集能力失败。

## 2026-07-15：harness 调整

按失败测试先行的方式完成以下调整：

1. 分页前把消息深链规范化为频道根路由。
2. 所有分页路由使用 cache-buster，避免复用同一 SPA 页面状态。
3. 发现 OpenCLI 的 Discord message request key 不包含 query 参数后，将 freshness 判断从单独的 key 改为 `request key + request URL`。
4. network entry 缺失时只允许一次带新 cache-buster 的重新 open，之后继续有限次数等待；仍失败则标记 `missing` 并保持旧 checkpoint。
5. 增加逐页阶段遥测：open、wait、network observation、detail、mapping、validation、persist、重试次数和 match state。

调整后完整确定性测试仍为 32/32 通过。

## 2026-07-15：bounded soak

- 14 页，202 条原始消息。
- 194 条 accepted，8 条 unresolved relation。
- 0 invalid，0 duplicate。
- 所有页面为 `matched_new`，checkpoint 成功推进。

## 2026-07-15：真实 1000+ 采集与恢复

- 第一轮真实采集不是依靠人工导出，而是由 collector 在 OpenCLI Browser Bridge 中实际获取消息。
- 运行过程中出现多次 network 空窗；每次都停止当前页、保留旧 checkpoint，再从 checkpoint 恢复。
- 第一轮最终形成 1392 条唯一 Canonical 消息，未出现 invalid 或重复 ID。
- 第二轮使用同一频道、Profile、contract 和末尾 checkpoint，生成新的 run ID，新增 112 条消息，0 duplicate、0 invalid。
- 两轮 evidence 合计 1504 条唯一 Canonical 消息。
- 人工操作仅用于登录、重新打开页面和诊断网络观测，没有向 evidence 写入或注入消息数据。

## 结果与后续影响

- OpenCLI Browser Bridge 可以作为后续采集设计的验证基础，但不能省略 freshness、有限重试、checkpoint-resume 和逐页 telemetry。
- 当前结论不是“单次运行永不失败”，而是“失败可定位、可恢复，且未确认数据不会推进 checkpoint”。
- Spike-01 完成后，下一门禁是独立的 Spike-02 Spec 和 Plan；本 Journal 不授权开始 Spike-02 或 V0/V1 生产实现。

## 2026-07-18：Active Adapter 作为后续 Discord 抓取方案

- 用户确认：后续 Discord 抓取采用 Active Adapter 方向，写 V0 Spec 时以此结论为前置设计输入。
- Active Adapter 不是第二套完整浏览器采集框架，而是基于 OpenCLI Browser Bridge，由项目侧主动控制频道规范化、分页、响应匹配、freshness、有限重试和失败分类的适配层；Canonical Schema、Evidence Store 和 checkpoint 边界保持不变。
- 后续验证证据为 Active Adapter 测试 24/24、原始 Spike-01 回归 32/32、1008 条原始/Canonical 消息处理、0 重复/无效消息和 checkpoint 恢复通过；但由于原始 Connector 对照运行使用了错误会话，未形成严格的同条件性能对比，长期无人值守稳定性也仍未完成验证。
- 决策：Active Adapter 作为未来 V0 Discord 抓取 Spec 的候选主路径；原始 OpenCLI Connector 保留为诊断基线和必要时的回退候选。该结论不等于生产批准，Active Adapter 代码暂不并入 main。
