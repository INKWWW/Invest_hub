# V1 Engineering Journal: Discord 正式可用 MVP

日期：2026-07-19（2026-07-20 更新）
阶段：V1 已部署；真实双来源有界 history 路径通过；正式可用 MVP 的剩余验收待执行

## 目标与边界

本阶段只实现 Discord 多来源阅读 MVP。浏览器 Profile、Cookie、真实 Discord URL、私有 Prompt、完整模型响应和本地 evidence 均不进入仓库、控制面 payload 或普通用户页面。

## 已实现的闭环

- 为来源授权、规则快照、有界增量/历史任务、批次摘要、日累计摘要和摘要收据增加数据库原子边界；checkpoint 只能在 receipt 与摘要 ID 匹配后推进。
- Worker 支持 owner-only 多来源配置、规则归因、最多 5 页的常规同步、显式 1–25 页历史任务和 Active Adapter freshness 失败分类。
- 管理员可以管理来源启停/Worker 绑定、作者规则和有界补采；普通用户可在 `/discord` 阅读共享的安全 DTO。
- 阅读页提供频道和日期选择、当前日累计摘要、批次展开、原始消息证据、摘要历史、处理中/失败状态与证据过期标记；不会输出 local raw ref、任务诊断、Worker、凭据、Prompt 或 Provider secret。
- 定时窗口固定为 Asia/Shanghai 的 08:00 与 20:50。数据库以 `(source_id, window_key)` 唯一键保证跨重启、跨进程重复 tick 返回同一任务；本地 Worker 至多补最近 48 小时的四个窗口，超出范围只记录脱敏 warning 并等待管理员创建有界历史任务。

## 2026-07-20 隔离部署与真实运行

- 专用 V1 Supabase 已应用 `001`–`006` 迁移并与本地迁移列表一致；Vercel 控制面已部署，未认证 reader API 仍返回 `401`。
- 管理员已在正式网页登录，创建两个逻辑来源并绑定同一个受权本地 Worker。真实频道 URL、Profile、Prompt、邀请码、凭据、模型响应和 evidence 均保持在仓库外的 owner-only 目录。
- 两个显式 `history`、`max_pages=1` 的真实任务均已成功。此前 Browser Bridge 未捕获网络响应时，一个来源保留为 `retryable_failed`；刷新并重新验证后，该任务按正式重试语义恢复为 `queued` 并成功完成。没有把 missing response 解释为无数据成功。
- 最终聚合验收只读取计数：`2` 个任务均为 `succeeded`、任务/原始/Canonical/当前摘要均覆盖 `2` 个来源；共持久化 `20` 条 raw、`20` 条 Canonical、`2` 次 structured run、`8` 条当前日摘要和 `40` 条 evidence reference。正文、URL、ID 和 Prompt 未写入本记录。
- 实测发现 LocalEvidenceStore 创建的文件权限可能受 umask 影响而宽于 owner-only。已将既有证据目录收紧为目录 `0700`、文件 `0600`，并补充 Worker 回归测试及实现，使今后新建 evidence 目录/文件强制为 `0700`/`0600`；本次本地 evidence 为 `12` 个文件，权限复核通过。

这些结果证明了专用部署、真实双来源有界 history、远程持久化和 retry 闭环；它们不替代增量二次去重、真实失败隔离、普通用户阅读和响应式视觉验收。

## 结论

V1 的代码、迁移、确定性验收、隔离部署与一次真实双来源有界 history 已完成；它仍不能称为“Discord 正式可用 MVP”。达成该称谓前，必须补齐真实双来源增量及二次去重/checkpoint、可操作的真实失败隔离、普通用户正式阅读和桌面/手机视觉验收，并完成一次基于真实运行的人工质量抽检。
