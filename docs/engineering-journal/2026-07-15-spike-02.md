# Spike-02 Engineering Journal

## 文档边界

本文档记录 Spike-02 执行期间实际发生的事件、尝试、失败和调整原因。它不是正式需求，也不是架构决策的唯一来源；正式范围以 Spec 为准，阶段结论以 Final Report 为准。

真实 Prompt、完整 Codex 响应和 evidence 保存在本地受保护目录，不进入 Git。本文只记录脱敏后的命令参数、计数、状态、耗时和技术现象，不记录消息正文、私有路径、Cookie、Token 或完整模型响应。

## 2026-07-15：进入独立 worktree

- 保持 Discovery 门禁：只修改 Spike harness、测试和治理文档，不初始化生产应用框架，不安装生产依赖。

## 2026-07-15：Codex CLI 边界与首次失败

- Provider 使用非交互 `codex exec`、`--sandbox read-only`、`--ephemeral` 和 `--output-last-message`。
- 初次真实运行没有允许 Codex 写入自身状态目录，12 次请求均因 state DB read-only / app-server 初始化失败而 `provider_failed`。
- 增加 `--add-dir <CODEX_HOME>` 后，直接 smoke test 成功；项目 worktree 仍保持只读边界。

## 2026-07-15：结构化输出校验调整

- 第一轮小批次请求进程和 JSON 看似成功，但模型返回了不符合约定的 `messages` 形状；原 parser 对缺失顶层字段默认空值，造成错误的成功判断。
- 将 Prompt 改为要求精确的 `topics`、`media_unparsed`、`warnings` 结构，并让 Schema Validator 拒绝缺失顶层字段。
- 后续运行暴露出 target topic 的 `author_id` 缺失。于是每条输入行增加 `author_id`、`author_scope` 和 `kind`，Prompt 明确要求精确归因，并禁止推测 `unparsed_media` 内容。

## 2026-07-15：小批次质量验证

- Codex CLI 版本：`codex-cli 0.144.3`；运行时报告模型：`gpt-5.6-luna`。
- 12 条公开 fixture、单 chunk 运行最终成功：最终成功率 100%，JSON/Schema 率 100%，耗时约 150,956 ms。
- 人工质量复核 6/6 claims covered、grounded、correct attribution；严重归因错误 0，媒体臆测 0。
- 未解析图片被标记为 `media_unparsed=true`，没有从图片内容生成结论。

## 2026-07-15：120 秒超时窗口问题

- 使用 chunk size 3、120 秒超时窗口时，多个 Codex 进程在约 126–137 秒被终止。
- 原始诊断显示模型已经生成合法 JSON，但仍在 WebSocket 重试和退出清理阶段；因此 120 秒会把可用输出误记为 timeout。
- 默认超时调整为 240 秒，并将该现象记录为限制，不把它计入成功率或忽略掉。

## 2026-07-15：500 条容量尝试

- 按计划使用 500 条、chunk size 25 运行；前 2/20 个 chunk 成功，耗时分别为 151.4 秒和 153.8 秒，均无重试。
- 按此观测，完整串行运行预计需要约 50–52 分钟，因此停止后续运行；该目录只作为局部容量 evidence，不作为完整 500 条通过结论。
- 之后尝试 chunk size 500。首个请求超过 240 秒后 runner 卡住，没有正常写出 timeout evidence。

## 2026-07-16：进程组终止与管道清理修复

- 根因定位：Codex 子进程可能产生继承 stdout/stderr 管道的后代进程；timeout 后只调用父进程 `kill()`，随后无界 `communicate()` 排空管道，造成 runner 卡死。
- 先添加回归测试，验证后代进程持有管道时旧实现会阻塞约 5.5 秒；再实现最小修复：独立进程组、终止整个进程组、stdout/stderr 写入临时文件、timeout 后有限等待并回收诊断。
- 修复后回归测试通过，完整 Spike-02 确定性测试为 35/35；此前的 runner 卡死不再复现。

## 2026-07-16：chunk size 500 和 250 复测

- 修复后重新测试 500 条、chunk size 500：首个 chunk 在 240,014 ms 正常记录为 timeout，进程组正常回收；停止后续重试。
- 回退测试 500 条、chunk size 250：首个 chunk 在 240,009 ms 正常记录为 timeout，进程组正常回收；停止后续重试。
- 两次结果说明当前 Codex CLI / Prompt 条件下，500 和 250 都不是安全配置；这不是上下文清理卡死，而是单 chunk 在 240 秒内无法完成。

## 2026-07-17：chunk size 250 重跑

- 使用 500 条 synthetic fixture、`chunk-size 250`、Codex CLI、单 chunk 240 秒超时和最多 3 次尝试重新运行；evidence 保存在本地受保护目录 `/private/tmp/invest-hub-spike-02-evidence/codex-500-c250-rerun-20260717`。
- chunk 0000 首次成功，耗时 77,235 ms；chunk 0001 三次均超时，耗时分别为 240,019 ms、240,017 ms、240,023 ms。
- 本轮共 4 次请求、2 次重试、2 个 chunk；最终成功率 50%，JSON/Schema 率 100%（仅对写入结果的记录），P50/P95 为 240,017/240,023 ms。
- 三次 timeout 均以退出码 `-9` 结束，进程组清理完成，CLI 正常输出汇总；因此当前问题不是此前的管道清理卡死，而是第二个 250-message chunk 在 240 秒窗口内不稳定/无法完成。
- 本轮没有改变 Spike-02 的 `unverified` 结论，也不支持把 `chunk-size 250` 作为安全配置；下一候选仍为 `chunk-size 100` 或更小。

## 2026-07-18：chunk size 100 容量验证

- 使用 500 条 synthetic fixture、`chunk-size 100`、Codex CLI、单 chunk 240 秒超时和最多 3 次尝试运行；evidence 保存在本地受保护目录 `/private/tmp/invest-hub-spike-02-evidence/codex-500-c100-20260718`。
- 共拆分为 5 个主 chunk，5/5 首次成功，最终成功率 100%，没有发生重试或 timeout；各 chunk 耗时为 120,403、120,272、123,354、124,058、157,740 ms。
- 本轮请求数 5、重试数 0、JSON/Schema 率 100%，P50/P95 为 123,354/157,740 ms，五个请求耗时合计 645,827 ms；所有 Codex 进程退出码均为 0，CLI 正常输出汇总。
- 该结果说明 100 比 250 更适合作为当前容量候选，但 synthetic fixture 只用于容量证据；1000 条容量、重复运行稳定性和业务质量仍未验证，Spike-02 结论保持 `unverified`。

## 2026-07-18：有界并发验证

- 在已批准的有界并发 Spec/Plan 下，保持每个 chunk 独立启动 `codex exec`，不复用 Codex 会话；新增最多 2 个 worker，默认 `max-concurrency=1` 保持串行兼容。
- EvidenceStore 对 JSON/JSONL 本地写入增加线程锁；活动请求计数只包住 `provider.complete()`，因此 `max_active_requests` 反映真实 Codex 请求并发，而不是文件写入或已完成 future 数量。
- 公开小 fixture smoke 使用 `chunk-size 3`、4 个 chunk、最多 2 并发：4/4 成功、0 重试，批次耗时 39,884 ms，`max_active_requests=2`；`requests.jsonl`、`results.jsonl` 和 raw response 文件数量均与请求数一致。
- 500 条 synthetic fixture 使用 `chunk-size 100`、最多 2 并发：5/5 首次及最终成功，0 重试，JSON/Schema 率 100%，P50/P95 为 127,935/129,800 ms，批次墙钟 321,965 ms，`max_active_requests=2`。
- 与串行 c100 基线的请求耗时合计 645,827 ms 对比，本轮观测 speedup 约 2.006x。该结果只证明 synthetic capacity 的批次吞吐改善，不证明业务质量，不覆盖 1000 条或重复稳定性，也不批准生产并发策略。

## 当前结论与后续

- Spike-02 结论保持 `unverified`：小批次结构化质量通过，500 条 c100 已完成串行和最多 2 并发的一次成功运行，但 1000 条真实容量和重复稳定性尚未通过验证。
- 下一步应使用 100 或更小完成 1000 条，并重复 500 条以验证稳定性，继续记录首次/最终成功率、JSON/Schema 率、P50/P95、失败分类、实际并发和总耗时。
- 在容量结论明确、后续正式 Spec 和 implementation plan 另行批准前，不启动 V0/V1 生产实现，也不把 Codex CLI 固化为最终生产架构。
